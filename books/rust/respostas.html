Q1

O que Rust quer de você

O artigo #01 diz que Rust oferece segurança de memória sem coletor de lixo. Que duas classes de bugs comuns em C e C++ o compilador do Rust impede, e qual é o preço que o programador paga por isso?

  • Uso de memória inválida: ponteiro solto (use after free), liberação dupla e leitura fora dos limites. O sistema de posse e empréstimo garante, em tempo de compilação, que nenhuma referência sobrevive ao valor que ela aponta; o acesso a vetores é verificado.
  • Corridas de dados: duas threads acessando o mesmo dado, ao menos uma escrevendo, sem sincronização. As regras de empréstimo e os traits Send e Sync tornam isso erro de compilação.

O preço é uma curva de aprendizado mais íngreme: o compilador recusa programas que talvez fossem corretos, e é preciso aprender a estruturar o código do jeito que ele consegue provar seguro. Em troca, uma classe inteira de falhas, que em C só aparece em produção, nem chega a compilar.

Q2

Imutável por padrão

Por que let x = 5; x = 6; não compila em Rust? Qual a diferença entre let mut, shadowing (let x = x + 1;) e const?

Variáveis são imutáveis por padrão: a mutação precisa ser pedida com mut, o que deixa visível, na declaração, quais valores mudam. O let mut x cria uma variável que pode receber novos valores do mesmo tipo. O shadowing cria uma variável nova com o mesmo nome, que esconde a anterior; ela pode até ter outro tipo (let espacos = " "; let espacos = espacos.len();), e a anterior continua imutável. O const é um valor conhecido em tempo de compilação, com tipo obrigatório, que pode ser global e é copiado onde é usado (const MAX_JOGADORES: u32 = 4;).

Q3

Expressão ou instrução

Por que a função abaixo não compila, e como corrigi-la com uma mudança de um caractere?

fn dobro(x: i32) -> i32 {
    x * 2;
}

Em Rust, quase tudo é expressão (produz um valor), e um bloco { ... } vale a sua última expressão, se ela não terminar em ponto e vírgula. O ; transforma x * 2 numa instrução, que vale () (a unidade); a função promete i32 e devolve (), e o compilador acusa "mismatched types". A correção é tirar o ponto e vírgula: x * 2. O mesmo princípio permite let nota = if pontos > 90 { 'A' } else { 'B' }; e let r = loop { ... break valor; };.

Q4

Estouro de inteiro

O que acontece em let x: u8 = 255; let y = x + 1; no modo debug e no modo release? Que métodos tornam a intenção explícita?

Em debug, o estouro aritmético faz o programa entrar em pânico ("attempt to add with overflow"); em release (-O), por padrão, o valor dá a volta (wrap) e y vale 0, sem aviso. (Quando o valor é uma constante conhecida, como aqui, o compilador já recusa na compilação.) Para não depender do modo, os inteiros têm métodos explícitos: checked_add devolve Option (None no estouro), wrapping_add dá a volta de propósito, saturating_add para no limite (255) e overflowing_add devolve o resultado e um bool.

Q5

Tipos e conversões

Escreva um programa que mostre: o maior u8 e o menor i16; a conversão com as de 300_i32 para u8 e de -1_i32 para u32; a conversão segura com u8::try_from; e as quatro formas de somar 250_u8 + 10 (checked, wrapping, saturating e overflowing).

fn main() {
    println!("u8::MAX = {}, i16::MIN = {}", u8::MAX, i16::MIN);
    println!("300 as u8 = {} | -1 as u32 = {}", 300_i32 as u8, -1_i32 as u32);

    for v in [42_i32, 300, -5] {
        match u8::try_from(v) {
            Ok(b) => println!("try_from({v}) = Ok({b})"),
            Err(e) => println!("try_from({v}) = Err({e})"),
        }
    }

    let x: u8 = 250;
    println!("checked:     {:?}", x.checked_add(10));
    println!("wrapping:    {}", x.wrapping_add(10));
    println!("saturating:  {}", x.saturating_add(10));
    println!("overflowing: {:?}", x.overflowing_add(10));
}
u8::MAX = 255, i16::MIN = -32768
300 as u8 = 44 | -1 as u32 = 4294967295
try_from(42) = Ok(42)
try_from(300) = Err(out of range integral type conversion attempted)
try_from(-5) = Err(out of range integral type conversion attempted)
checked:     None
wrapping:    4
saturating:  255
overflowing: (4, true)

O as entre inteiros nunca falha: trunca os bits que não cabem (300 é 0x12C, e sobra 0x2C = 44) e reinterpreta o sinal (-1 vira o maior u32). Por isso é a escolha errada para dados vindos de fora; o try_from devolve um Result e obriga a tratar o caso que não cabe.

Q6

Expressões que devolvem valores

Escreva fn classificar(nota: u32) -> &'static str usando match com faixas (90..=100), uma função fn primeiro_divisor(n: u32) -> u32 que use loop com break valor, e um laço com rótulo ('externo) que pare os dois laços quando achar o primeiro par (a, b) com a * b == 42 e a < b.

fn classificar(nota: u32) -> &'static str {
    match nota {
        90..=100 => "A",
        70..=89 => "B",
        50..=69 => "C",
        0..=49 => "D",
        _ => "nota inválida",
    }
}

fn primeiro_divisor(n: u32) -> u32 {
    let mut d = 2;
    loop {
        if n % d == 0 {
            break d; // o loop "vale" d
        }
        d += 1;
    }
}

fn main() {
    for n in [95, 72, 40, 120] {
        println!("{n}: {}", classificar(n));
    }
    println!("primeiro divisor de 91: {}", primeiro_divisor(91));

    let mut achado = None;
    'externo: for a in 1..=42 {
        for b in a + 1..=42 {
            if a * b == 42 {
                achado = Some((a, b));
                break 'externo;
            }
        }
    }
    println!("primeiro par: {achado:?}");
}
95: A
72: B
40: D
120: nota inválida
primeiro divisor de 91: 7
primeiro par: Some((1, 42))

O match sobre um u32 precisa ser exaustivo: sem o braço _, o compilador recusa, porque valores acima de 100 não estariam cobertos. O loop é o único laço que pode devolver valor com break, porque é o único que o compilador sabe que só termina pelo break. O rótulo evita a variável "achei" e o segundo break que o C exigiria.

Q7

As três regras da posse

Enuncie as regras de ownership e explique por que let s1 = String::from("oi"); let s2 = s1; println!("{s1}"); não compila, enquanto o mesmo código com i32 compila.

  1. Cada valor tem um único dono (uma variável).
  2. Só pode haver um dono por vez.
  3. Quando o dono sai de escopo, o valor é liberado (drop).

A String guarda os caracteres no heap. let s2 = s1; move a posse: copia o ponteiro, o tamanho e a capacidade, e invalida s1, para que o heap não seja liberado duas vezes quando as duas saírem de escopo. Usar s1 depois é "borrow of moved value". O i32 vive todo na pilha e implementa o trait Copy: a atribuição copia os bits, e as duas variáveis continuam válidas. Para duplicar uma String, pede-se explicitamente: s1.clone(), e a cópia cara fica visível no código.

Q8

Uma mutável ou várias imutáveis

Qual é a regra dos empréstimos, e que bug clássico de C++ ela impede no código abaixo?

let mut v = vec![1, 2, 3];
let primeiro = &v[0];
v.push(4);
println!("{primeiro}");

Em qualquer momento, pode haver várias referências imutáveis (&T) ou uma única mutável (&mut T), nunca as duas ao mesmo tempo. Aqui, primeiro é um empréstimo imutável de v, ainda usado no println!, e o push precisa de um empréstimo mutável: o compilador recusa. O motivo é concreto: o push pode realocar o vetor, e primeiro apontaria para memória liberada, exatamente a invalidação de iteradores do std::vector em C++, que lá compila e falha em execução. Graças às non-lexical lifetimes, se primeiro não fosse usado depois do push, o código compilaria: o empréstimo acaba no último uso.

Q9

String e &str

Qual a diferença entre String e &str? Por que uma função que só lê um texto deve receber &str?

A String é dona de um texto UTF-8 no heap, que pode crescer e mudar. O &str é uma fatia emprestada (um ponteiro e um tamanho) de um texto que pertence a outro: uma String, um literal (que vive no binário, &'static str) ou parte de outro texto. Uma função que só lê deve receber &str porque aceita os três casos: uma &String converte sozinha para &str (deref coercion), e um literal já é &str. Receber String obrigaria quem chama a entregar a posse ou a clonar; receber &String recusaria literais sem uma conversão.

Q10

Movimento, cópia e empréstimo

Escreva um programa que mostre: (a) uma String movida para uma função e devolvida no retorno; (b) a mesma função reescrita para receber &str; (c) uma função que recebe &mut String e acrescenta texto; (d) um struct com #[derive(Clone, Copy)] sendo copiado.

fn consome(s: String) -> String {
    format!("{s}!") // recebe a posse e devolve uma String nova
}

fn tamanho(s: &str) -> usize {
    s.chars().count()
}

fn exclamar(s: &mut String) {
    s.push_str("!!");
}

#[derive(Debug, Clone, Copy)]
struct Ponto {
    x: i32,
    y: i32,
}

fn main() {
    let s = String::from("ação");
    let s = consome(s); // s foi movida e recebemos outra de volta
    println!("(a) {s}");

    println!("(b) {} caracteres, {} bytes", tamanho(&s), s.len());

    let mut grito = String::from("socorro");
    exclamar(&mut grito);
    println!("(c) {grito}");

    let p = Ponto { x: 1, y: 2 };
    let mut q = p; // cópia: Ponto é Copy
    q.x = 10;
    println!("(d) p = ({}, {}), q = ({}, {})", p.x, p.y, q.x, q.y);
}
(a) ação!
(b) 5 caracteres, 7 bytes
(c) socorro!!
(d) p = (1, 2), q = (10, 2)

O len() conta bytes (UTF-8), e o chars().count(), caracteres: "ação!" tem 5 caracteres e 7 bytes. Um struct só pode ser Copy se todos os campos forem Copy; com um campo String, o derive(Copy) não compila, porque copiar os bits duplicaria o dono do heap.

Q11

Slices e a primeira palavra

Escreva fn primeira_palavra(s: &str) -> &str que devolva a primeira palavra (até o primeiro espaço) como uma fatia do texto original, sem alocar. Mostre que tentar esvaziar a String (clear) enquanto a fatia ainda está em uso não compila (em comentário), e use a função com um literal e com uma String.

fn primeira_palavra(s: &str) -> &str {
    match s.find(' ') {
        Some(i) => &s[..i],
        None => s,
    }
}

fn main() {
    let mut frase = String::from("Ferris é o caranguejo");
    let p = primeira_palavra(&frase);
    // frase.clear(); // erro: frase está emprestada (imutável) para p, que é usada abaixo
    println!("primeira palavra: {p}");

    frase.clear(); // aqui pode: o empréstimo de p já terminou
    println!("frase vazia? {}", frase.is_empty());

    println!("de um literal: {}", primeira_palavra("Rust"));

    let numeros = [10, 20, 30, 40, 50];
    let meio: &[i32] = &numeros[1..4];
    println!("fatia de array: {meio:?}, soma {}", meio.iter().sum::<i32>());
}
primeira palavra: Ferris
frase vazia? true
de um literal: Rust
fatia de array: [20, 30, 40], soma 90

A fatia devolvida carrega um vínculo com a String original (um lifetime, que o compilador deduziu sozinho aqui): enquanto ela for usada, a String não pode ser alterada nem liberada. Em C, a função devolveria um char* para dentro do texto, e um clear antes do uso produziria lixo sem nenhum aviso. Cuidado com fatias de texto: &s[..i] com i no meio de um caractere de dois bytes (como o "é") entra em pânico; o find devolve sempre um índice de início de caractere, por isso aqui é seguro.

Q12

Option no lugar de null

Por que Rust não tem null? O que o Option<T> obriga o programador a fazer que um ponteiro nulo não obriga?

Tony Hoare, o criador da referência nula, a chamou de "erro de um bilhão de dólares": qualquer referência pode ser nula, e o tipo não diz quais. Em Rust, uma referência sempre aponta para algo válido, e a ausência é um tipo próprio: Option<T>, com os casos Some(valor) e None. Um Option<String> não é uma String: para usar o valor, é preciso tratá-lo (com match, if let, ?, unwrap_or e afins), e o compilador não deixa esquecer o caso None. A ausência deixa de ser uma surpresa em execução e passa a ser uma informação no tipo. E não custa memória a mais: um Option<&T> ou Option<Box<T>> ocupa o mesmo que o ponteiro, porque o None é representado pelo endereço zero, que uma referência nunca tem.

Q13

O operador ?

O que o operador ? faz numa função que devolve Result<T, E>? Por que unwrap() é aceitável num exemplo e perigoso numa biblioteca?

Aplicado a um Result, o ? devolve o valor se for Ok, ou retorna imediatamente da função com o Err, convertendo o tipo do erro com From se for preciso. Substitui o match repetido a cada chamada que pode falhar, mantendo a propagação explícita (cada ponto de falha tem o seu ? visível). O unwrap() extrai o valor ou entra em pânico: num exemplo ou num teste, ele encurta o código e a falha é aceitável; numa biblioteca, derruba o programa de quem a usa por um erro que ele poderia ter tratado. Fora de testes, prefira ?, ou expect("motivo") quando a falha realmente for um bug impossível, com a explicação de por quê.

Q14

Enum com dados

Como um enum do Rust difere de um enum do C? Mostre um enum Mensagem com quatro variantes de formatos diferentes.

No C, um enum é só um conjunto de inteiros com nome. No Rust, cada variante pode carregar dados próprios, com formatos diferentes, e o compilador sabe sempre qual variante está guardada (é a união etiquetada, segura):

enum Mensagem {
    Sair,                        // sem dados
    Mover { x: i32, y: i32 },    // campos nomeados
    Escrever(String),            // um valor
    MudarCor(u8, u8, u8),        // uma tupla
}

Um match sobre uma Mensagem precisa tratar as quatro variantes, e cada braço extrai os dados da sua (Mensagem::Mover { x, y } => ...). Acrescentar uma variante faz o compilador apontar cada match que ficou incompleto. Option e Result são enums comuns da biblioteca padrão, definidos assim.

Q15

Uma struct com métodos

Escreva struct Retangulo { largura: f64, altura: f64 } com um construtor associado quadrado(lado), os métodos area(&self), escalar(&mut self, fator) e cabe_em(&self, outro: &Retangulo) -> bool, e implemente o trait Display para imprimi-lo como 3x4.

use std::fmt;

#[derive(Debug, Clone, PartialEq)]
struct Retangulo {
    largura: f64,
    altura: f64,
}

impl Retangulo {
    fn quadrado(lado: f64) -> Self {
        Self { largura: lado, altura: lado }
    }
    fn area(&self) -> f64 {
        self.largura * self.altura
    }
    fn escalar(&mut self, fator: f64) {
        self.largura *= fator;
        self.altura *= fator;
    }
    fn cabe_em(&self, outro: &Retangulo) -> bool {
        self.largura <= outro.largura && self.altura <= outro.altura
    }
}

impl fmt::Display for Retangulo {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "{}x{}", self.largura, self.altura)
    }
}

fn main() {
    let mut r = Retangulo { largura: 3.0, altura: 4.0 };
    let q = Retangulo::quadrado(5.0);
    println!("{r} tem área {}; cabe em {q}? {}", r.area(), r.cabe_em(&q));
    r.escalar(2.0);
    println!("escalado: {r} (Debug: {r:?}); cabe agora? {}", r.cabe_em(&q));
    println!("igual a 6x8? {}", r == Retangulo { largura: 6.0, altura: 8.0 });
}
3x4 tem área 12; cabe em 5x5? true
escalado: 6x8 (Debug: Retangulo { largura: 6.0, altura: 8.0 }); cabe agora? false
igual a 6x8? true

O primeiro parâmetro diz o que o método faz com o objeto: &self só lê, &mut self altera, e self consumiria o valor. A chamada r.escalar(2.0) empresta r como mutável sozinha (auto-referencing), o que exige let mut r. O Display é para pessoas; o Debug (derivado) é para o programador. O PartialEq derivado compara campo a campo.

Q16

Uma máquina de estados com enum

Modele um pedido com enum Estado { Novo, Pago { valor: u32 }, Enviado { codigo: String }, Cancelado { motivo: String } } e escreva fn avancar(estado: Estado, evento: Evento) -> Result<Estado, String> com match sobre a tupla (estado, evento). Rode uma sequência válida e duas inválidas.

#[derive(Debug)]
enum Estado {
    Novo,
    Pago { valor: u32 },
    Enviado { codigo: String },
    Cancelado { motivo: String },
}

#[derive(Debug)]
enum Evento {
    Pagar(u32),
    Enviar(String),
    Cancelar(String),
}

fn avancar(estado: Estado, evento: Evento) -> Result<Estado, String> {
    match (estado, evento) {
        (Estado::Novo, Evento::Pagar(valor)) if valor > 0 => Ok(Estado::Pago { valor }),
        (Estado::Pago { .. }, Evento::Enviar(codigo)) => Ok(Estado::Enviado { codigo }),
        (Estado::Novo | Estado::Pago { .. }, Evento::Cancelar(motivo)) => Ok(Estado::Cancelado { motivo }),
        (e, ev) => Err(format!("não dá para {ev:?} no estado {e:?}")),
    }
}

fn descrever(e: &Estado) -> String {
    match e {
        Estado::Novo => "novo".to_string(),
        Estado::Pago { valor } => format!("pago (R$ {},{:02})", valor / 100, valor % 100),
        Estado::Enviado { codigo } => format!("enviado, rastreio {codigo}"),
        Estado::Cancelado { motivo } => format!("cancelado: {motivo}"),
    }
}

fn main() {
    let mut estado = Estado::Novo;
    for ev in [Evento::Pagar(4990), Evento::Enviar("BR123".into())] {
        estado = avancar(estado, ev).expect("sequência válida");
        println!("-> {}", descrever(&estado));
    }
    println!("{}", avancar(estado, Evento::Cancelar("desisti".into())).unwrap_err());
    println!("{}", avancar(Estado::Novo, Evento::Pagar(0)).unwrap_err());
    let pago = avancar(Estado::Novo, Evento::Pagar(2500)).unwrap();
    println!("-> {}", descrever(&avancar(pago, Evento::Cancelar("endereço errado".into())).unwrap()));
}
-> pago (R$ 49,90)
-> enviado, rastreio BR123
não dá para Cancelar("desisti") no estado Enviado { codigo: "BR123" }
não dá para Pagar(0) no estado Novo
-> cancelado: endereço errado

Cada estado carrega só os dados que fazem sentido nele: um pedido Novo não tem código de rastreio, e não existe um campo codigo vazio esperando ser preenchido. A guarda if valor > 0 refina o padrão. Como avancar recebe o estado por valor, o estado antigo é consumido e não pode ser usado por engano depois da transição.

Q17

Erros próprios e o operador ?

Escreva fn ler_config(texto: &str) -> Result<Config, ErroConfig> que leia linhas chave=valor com as chaves porta (número de 1 a 65535) e host (obrigatório). Defina enum ErroConfig com as variantes LinhaInvalida(usize), Faltando(&'static str) e Porta(std::num::ParseIntError), implemente Display e From<ParseIntError>, e use o ?.

use std::fmt;
use std::num::ParseIntError;

#[derive(Debug)]
struct Config {
    host: String,
    porta: u16,
}

#[derive(Debug)]
enum ErroConfig {
    LinhaInvalida(usize),
    Faltando(&'static str),
    Porta(ParseIntError),
}

impl fmt::Display for ErroConfig {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            ErroConfig::LinhaInvalida(n) => write!(f, "linha {n} não está no formato chave=valor"),
            ErroConfig::Faltando(chave) => write!(f, "falta a chave '{chave}'"),
            ErroConfig::Porta(e) => write!(f, "porta inválida: {e}"),
        }
    }
}

impl From<ParseIntError> for ErroConfig {
    fn from(e: ParseIntError) -> Self {
        ErroConfig::Porta(e)
    }
}

fn ler_config(texto: &str) -> Result<Config, ErroConfig> {
    let (mut host, mut porta) = (None, 8080);
    for (i, linha) in texto.lines().enumerate().filter(|(_, l)| !l.trim().is_empty()) {
        let (chave, valor) = linha.split_once('=').ok_or(ErroConfig::LinhaInvalida(i + 1))?;
        match chave.trim() {
            "host" => host = Some(valor.trim().to_string()),

            _ => {} // chaves desconhecidas são ignoradas
        }
    }
    let host = host.ok_or(ErroConfig::Faltando("host"))?;
    if porta == 0 {
        return Err(ErroConfig::LinhaInvalida(0));
    }
    Ok(Config { host, porta })
}

        "host = x\nisto não é config",

Q18

iter, iter_mut e into_iter

Qual a diferença entre percorrer um Vec<String> com v.iter(), v.iter_mut() e v.into_iter() (ou for x in v)? O que acontece com v depois do último?

  • iter() empresta os elementos: cada item é &String. O vetor continua intacto.
  • iter_mut() empresta mutavelmente: cada item é &mut String, e pode ser alterado no lugar.
  • into_iter() consome o vetor: cada item é a String em si, com a posse. Depois dele, v foi movido e não pode mais ser usado.

O for x in &v equivale ao iter(), o for x in &mut v ao iter_mut(), e o for x in v ao into_iter(). Escolher o certo é dizer, no código, se você só olha, se altera ou se fica com os elementos.

Q19

Iteradores preguiçosos e de custo zero

Por que v.iter().map(|x| x * 2); sozinho não faz nada (e o compilador avisa)? O que significa dizer que os iteradores do Rust são uma "abstração de custo zero"?

Os adaptadores (map, filter, take...) são preguiçosos: só montam a cadeia. Nada é calculado até que um consumidor (collect, sum, for, count) peça os itens, e o compilador avisa "*unused Map that must be used*". "Custo zero" quer dizer que a cadeia v.iter().filter(...).map(...).sum() compila, depois das otimizações, para um código de máquina tão rápido quanto o laço escrito à mão: o compilador funde os passos, elimina as verificações de limite que sabe desnecessárias e, muitas vezes, vetoriza. A abstração é para quem lê; o processador não paga por ela.

Q20

Fn, FnMut e FnOnce

Qual a diferença entre os traits Fn, FnMut e FnOnce? Dê uma closure de cada tipo.

Eles dizem o que a closure faz com o que capturou:

  • **Fn: só lê** as capturas; pode ser chamada várias vezes, inclusive em paralelo. let soma = |x| x + base;
  • **FnMut: altera** as capturas; pode ser chamada várias vezes, mas exige acesso exclusivo. let mut conta = || { contador += 1; };
  • **FnOnce: consome** algo capturado; só pode ser chamada uma vez. let entrega = move || nome; (devolve a String, que deixa de existir na closure).

Toda Fn é também FnMut e FnOnce. Uma função que recebe closures pede o trait menos exigente que lhe basta: thread::spawn pede FnOnce, porque a closure roda uma vez; sort_by pede FnMut.

Closures que capturam

Escreva fn criar_contador(inicio: i32, passo: i32) -> impl FnMut() -> i32, que devolve uma closure com estado próprio; uma função genérica fn aplicar_duas_vezes<F: Fn(i32) -> i32>(f: F, x: i32) -> i32; e mostre o move necessário para devolver uma closure que captura uma variável local.

fn criar_contador(inicio: i32, passo: i32) -> impl FnMut() -> i32 {
    let mut atual = inicio;
    move || {
        let r = atual;
        atual += passo;
        r
    }
}

fn aplicar_duas_vezes<F: Fn(i32) -> i32>(f: F, x: i32) -> i32 {
    f(f(x))
}

fn somador(n: i32) -> impl Fn(i32) -> i32 {
    move |x| x + n // sem move, a closure tentaria emprestar n, que morre no fim da função
}

fn main() {
    let mut de2 = criar_contador(0, 2);
    let mut de10 = criar_contador(100, -10);
    let seq: Vec<_> = (0..4).map(|_| (de2(), de10())).collect();
    println!("{seq:?}");

    let mais5 = somador(5);
    println!("aplicar_duas_vezes(+5, 1) = {}", aplicar_duas_vezes(&mais5, 1));
    println!("aplicar_duas_vezes(x*3, 2) = {}", aplicar_duas_vezes(|x| x * 3, 2));
}

Q24

Genérico ou dyn Trait

Compare fn desenhar<T: Forma>(f: &T) e fn desenhar(f: &dyn Forma). Quando usar cada um?

  • Genérico (T: Forma, ou impl Forma): despacho estático. O compilador gera uma cópia da função para cada tipo usado (monomorfização), e cada chamada é direta e pode ser embutida (inlining). Mais rápido; executável maior; e um Vec<T> só guarda um tipo.
  • **dyn Forma: despacho dinâmico**, por uma tabela de métodos (vtable), como as funções virtuais do C++. Uma cópia só da função, e um Vec<Box<dyn Forma>> guarda círculos e quadrados juntos; cada chamada passa por um ponteiro.

Use genéricos por padrão, em bibliotecas e caminhos críticos; use dyn quando a coleção é heterogênea, quando o tipo é escolhido em execução (um plugin, uma configuração) ou para reduzir o tamanho do binário e o tempo de compilação.

Q25

A regra do órfão

Por que você pode implementar o seu trait Resumo para Vec<i32>, e o trait Display para o seu struct Livro, mas não pode implementar Display para Vec<i32>? Como contornar?

É a regra do órfão (coherence): uma implementação de trait para um tipo só é permitida se o trait ou o tipo for definido na sua crate. Display e Vec são da biblioteca padrão; se qualquer crate pudesse implementar Display for Vec<i32>, duas dependências poderiam fazê-lo de formas diferentes, e o compilador não teria como escolher. O contorno é o padrão newtype: struct Lista(Vec<i32>);, um tipo seu que envolve o outro, sem custo em execução, para o qual você implementa o que quiser.

Q26

Por que lifetimes

Por que esta função não compila sem a anotação de lifetime? O que 'a promete?

fn maior(a: &str, b: &str) -> &str {
    if a.len() >= b.len() { a } else { b }
}

O retorno é uma referência, e o compilador precisa saber a qual dos parâmetros ela está ligada, para garantir que ela não sobreviva ao valor emprestado. Como ela pode vir de a ou de b, ele não consegue deduzir sozinho e pede a anotação: fn maior<'a>(a: &'a str, b: &'a str) -> &'a str. O 'a promete que o resultado vive no máximo tanto quanto o menor dos dois empréstimos. Ele não muda quanto tempo nada vive: só descreve a relação, para que o compilador recuse um uso do resultado depois que uma das origens morreu. Nas funções com uma só referência de entrada, as regras de elisão fazem a dedução, e a anotação não é necessária.

fn maior_e_menor<T: PartialOrd + Copy>(itens: &[T]) -> Option<(T, T)> {
    let (&primeiro, resto) = itens.split_first()?;
    let mut menor = primeiro;
    let mut maior = primeiro;
    for &x in resto {
        if x < menor {
            menor = x;
        }
        if x > maior {
            maior = x;
        }
    }
    Some((maior, menor))
}

struct Par<T> {
    a: T,
    b: T,
}

impl<T: PartialOrd> Par<T> {
    fn maior(&self) -> &T {
        if self.a >= self.b { &self.a } else { &self.b }
    }
}

fn main() {
    println!("{:?}", maior_e_menor(&[3, 9, -2, 7]));
    println!("{:?}", maior_e_menor(&[2.5, -0.5, 1.0]));
    println!("{:?}", maior_e_menor(&['r', 'u', 's', 't']));
    println!("{:?}", maior_e_menor::<i32>(&[]));
    println!("maior do par: {}", Par { a: "pera", b: "uva" }.maior());

Q30

Crate, módulo e visibilidade

Qual a diferença entre crate, package e módulo? O que pub, pub(crate) e a ausência de modificador significam para uma função dentro de mod banco?

Uma crate é a unidade de compilação: uma biblioteca (lib.rs) ou um executável (main.rs). Um package é o que o Cargo.toml descreve: uma ou mais crates (no máximo uma biblioteca). Os módulos organizam o código dentro de uma crate, como pastas de namespaces, e cada arquivo é um módulo. Sem modificador, um item é privado ao módulo em que foi declarado (e visível nos filhos dele); pub(crate) o torna visível em toda a crate, mas não para quem a usa como dependência; pub o torna público, inclusive fora da crate, desde que o caminho até ele também seja público. O padrão privado faz da API pública uma decisão explícita.

Q31

Onde ficam os testes

No Rust, por que os testes unitários ficam no mesmo arquivo do código (#[cfg(test)] mod tests), e os de integração na pasta tests/? O que um teste de integração não consegue acessar?

Os testes unitários ficam junto do código para testarem também funções privadas: como mod tests é um módulo filho, enxerga tudo o que o pai tem. O #[cfg(test)] faz o módulo ser compilado só no cargo test, sem entrar no binário final. Os testes de integração, na pasta tests/, são compilados como crates separadas que usam a sua biblioteca como um usuário externo: só enxergam a API pública. Eles verificam que as partes funcionam juntas pela porta da frente, e não conseguem acessar nada privado. Há ainda os testes de documentação: os exemplos dos comentários /// são compilados e executados pelo cargo test, o que garante que a documentação não mente.

Q33

Box, Rc e RefCell

Para que serve cada um: Box<T>, Rc<T> e RefCell<T>? Por que Rc<RefCell<T>> é uma combinação comum, e qual é o risco dela?

  • **Box<T>: um valor no heap com um** dono. Serve para tipos recursivos (uma lista ou uma árvore precisa de tamanho conhecido), para objetos grandes que se movem barato e para dyn Trait.
  • **Rc<T>: posse compartilhada** com contagem de referências, numa thread só. O valor vive enquanto houver um Rc apontando para ele. Só dá acesso de leitura.
  • **RefCell<T>: mutabilidade interior. Permite alterar o valor por uma referência imutável, verificando as regras de empréstimo em execução**: dois borrow_mut() ativos ao mesmo tempo causam pânico.

O Rc<RefCell<T>> dá "vários donos que podem alterar", como num grafo de objetos. O risco é duplo: as violações de empréstimo, que antes eram erro de compilação, viram pânico em execução; e dois Rc que se apontam formam um ciclo que nunca é liberado. O Weak<T> quebra o ciclo, como o weak_ptr do C++.

Q34

Send e Sync

O que significam os traits Send e Sync? Por que thread::spawn recusa uma closure que captura um Rc<T>, e aceita uma com Arc<T>?

Um tipo é **Send se pode ser transferido para outra thread, e Sync se pode ser compartilhado** entre threads por referência (&T é Send). O compilador os implementa sozinho para os tipos cujas partes também os implementam. O Rc<T> atualiza o contador com operações comuns, não atômicas: duas threads clonando o mesmo Rc corromperiam a contagem. Por isso ele não é Send, e o spawn, que exige Send na closure, recusa. O Arc<T> (atomic Rc) usa operações atômicas no contador e é Send e Sync quando T é. Para alterar o dado compartilhado, combina-se com Mutex ou RwLock: Arc<Mutex<T>>. É assim que a corrida de dados vira erro de compilação.

Q35

Thread ou async

Quando usar threads e quando usar async com Tokio? Por que chamar uma função bloqueante (std::thread::sleep, leitura síncrona de arquivo grande) dentro de uma tarefa async é um erro?

Threads servem para trabalho de CPU em paralelo e para poucas tarefas concorrentes: cada uma tem a sua pilha e é agendada pelo sistema operacional. Async serve para muitas tarefas que passam a maior parte do tempo esperando E/S (milhares de conexões de rede): cada tarefa é uma máquina de estados pequena, e um punhado de threads do runtime alterna entre elas a cada .await. A troca é cooperativa: uma tarefa só cede a thread num .await. Uma chamada bloqueante prende a thread do runtime, e todas as outras tarefas agendadas nela param junto. O certo é usar as versões assíncronas (tokio::time::sleep, tokio::fs) ou mandar o trabalho bloqueante para tokio::task::spawn_blocking.

Q36

macro_rules ou função

Quando uma macro declarativa (macro_rules!) é justificada, e quando uma função resolve? Por que println! e vec! precisam ser macros?

Uma macro opera sobre código, na compilação: pode receber um número variável de argumentos, de tipos diferentes, gerar itens (funções, impl) e receber trechos de sintaxe. O println! precisa ser macro porque recebe uma quantidade variável de argumentos e verifica a string de formato contra eles na compilação; o vec![1, 2, 3] também aceita quantos elementos houver. Quando uma função genérica resolve, ela é melhor: tem tipos claros, mensagens de erro legíveis, aparece na documentação e não surpreende quem lê. As macros procedurais (#[derive(...)]) vão além e geram implementações a partir da definição de um tipo.

Q38

Uma árvore com Rc, RefCell e Weak

Monte uma árvore de categorias (Livros → Ficção → Romance) em que cada nó tem filhos: RefCell<Vec<Rc<No>>> e pai: RefCell<Weak<No>>. Mostre o caminho de um nó até a raiz, as contagens forte e fraca, e que todos os nós são liberados no fim (com um Drop que imprime).

use std::cell::RefCell;
use std::rc::{Rc, Weak};

struct No {
    nome: String,
    filhos: RefCell<Vec<Rc<No>>>,
    pai: RefCell<Weak<No>>,
}

impl Drop for No {
    fn drop(&mut self) {
        println!("liberado: {}", self.nome);
    }
}

fn novo(nome: &str) -> Rc<No> {
    Rc::new(No { nome: nome.into(), filhos: RefCell::new(vec![]), pai: RefCell::new(Weak::new()) })
}

fn ligar(pai: &Rc<No>, filho: &Rc<No>) {
    *filho.pai.borrow_mut() = Rc::downgrade(pai);
    pai.filhos.borrow_mut().push(Rc::clone(filho));
}

fn main() {
    let raiz = novo("Livros");
    {
        let ficcao = novo("Ficção");
        let romance = novo("Romance");
        ligar(&raiz, &ficcao);
        ligar(&ficcao, &romance);

        let mut caminho = vec![romance.nome.clone()];
        let mut atual = romance.pai.borrow().upgrade();
        while let Some(no) = atual {
            caminho.push(no.nome.clone());
            atual = no.pai.borrow().upgrade();
        }
        println!("caminho: {}", caminho.join(" <- "));
        println!("Ficção: {} fortes, {} fraca(s)", Rc::strong_count(&ficcao), Rc::weak_count(&ficcao));
    }
    println!("fim do bloco: os nós continuam vivos pela raiz ({} filho)", raiz.filhos.borrow().len());
}
caminho: Romance <- Ficção <- Livros
Ficção: 2 fortes, 1 fraca(s)
fim do bloco: os nós continuam vivos pela raiz (1 filho)
liberado: Livros
liberado: Ficção
liberado: Romance

"Ficção" tem dois donos fortes (a variável local e o vetor de filhos da raiz) e uma referência fraca (a do "Romance" para o pai). As referências fracas para o pai são o que permite a liberação: se o pai fosse Rc, pai e filho se manteriam vivos para sempre, e nenhuma linha "liberado" apareceria. O upgrade() devolve Option<Rc<No>>: None se o pai já tiver sido liberado. A ordem da liberação é de cima para baixo: quando a raiz morre, o vetor dela solta o último dono da "Ficção", e assim por diante.

Q39

Soma em paralelo com scoped threads

Some os números de 1 a 10 milhões dividindo o intervalo entre 4 threads com std::thread::scope, que permite às threads emprestar dados da pilha do main sem Arc. Depois faça um contador compartilhado com Arc<Mutex<u64>> e outro com AtomicU64, e confira os três resultados.

use std::sync::atomic::{AtomicU64, Ordering};
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let numeros: Vec<u64> = (1..=10_000_000).collect();
    let partes = 4;
    let tamanho = numeros.len().div_ceil(partes);

    let soma: u64 = thread::scope(|s| {
        let tarefas: Vec<_> = numeros.chunks(tamanho).map(|c| s.spawn(move || c.iter().sum::<u64>())).collect();
        tarefas.into_iter().map(|t| t.join().unwrap()).sum()
    });
    println!("scope:  {soma}");

    let protegido = Arc::new(Mutex::new(0u64));
    let atomico = Arc::new(AtomicU64::new(0));
    let mut threads = vec![];
    for _ in 0..4 {
        let (p, a) = (Arc::clone(&protegido), Arc::clone(&atomico));
        threads.push(thread::spawn(move || {
            for _ in 0..100_000 {
                *p.lock().unwrap() += 1;
                a.fetch_add(1, Ordering::Relaxed);
            }
        }));
    }
    for t in threads {
        t.join().unwrap();
    }
    println!("mutex:  {}", protegido.lock().unwrap());
    println!("atomic: {}", atomico.load(Ordering::Relaxed));
    println!("fórmula: {}", 10_000_000u64 * 10_000_001 / 2);
}

mutex:  400000
atomic: 400000
fórmula: 50000005000000

O thread::scope garante que todas as threads terminam antes de ele retornar, e por isso elas podem receber fatias (&[u64]) do vetor do main: o compilador sabe que o empréstimo não sobrevive aos dados. Com thread::spawn comum, a closure precisa ser 'static, e o vetor teria de ir num Arc. O lock() devolve um guard que destrava o mutex ao sair de escopo, o RAII do Rust; e não há como acessar o dado sem travá-lo, porque ele fica dentro do Mutex. O Ordering::Relaxed basta para um contador; para publicar dados entre threads, é preciso Release e Acquire.

Q40

Produtor e consumidor com canais

Use std::sync::mpsc para que três produtores enviem pedidos ((produtor, número)) a um consumidor, que os processa até todos os produtores terminarem. Mostre como o consumidor sabe que acabou e por que o drop do transmissor original é necessário.

use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel::<(u32, u32)>();

    for produtor in 1..=3 {
        let tx = tx.clone();
        thread::spawn(move || {
            for n in 1..=2 {
                tx.send((produtor, n)).unwrap();
            }
        }); // o clone de tx é liberado aqui
    }
    drop(tx); // sem isso, o rx esperaria para sempre pelo tx original

    let mut recebidos: Vec<_> = rx.iter().collect(); // termina quando todos os tx morrem
    recebidos.sort();
    println!("{} pedidos: {recebidos:?}", recebidos.len());
}
6 pedidos: [(1, 1), (1, 2), (2, 1), (2, 2), (3, 1), (3, 2)]

O rx.iter() bloqueia esperando mensagens e só termina quando todos os transmissores foram liberados: é assim que o consumidor sabe que acabou, sem sentinela. Cada produtor tem o seu clone, mas o tx original, criado no main, ainda existe até o drop explícito. O sort é só para a saída ficar previsível, porque a ordem de chegada depende do agendamento das threads. O send move o valor para o canal: depois de enviado, o produtor não tem mais acesso a ele, e a corrida de dados é impossível por construção. "Não se comunique compartilhando memória; compartilhe memória comunicando-se."

Tarefas assíncronas com Tokio

Num projeto Cargo com tokio = { version = "1", features = ["full"] }, escreva um programa que dispare três "consultas" a fornecedores com tempos diferentes (tokio::time::sleep), espere todas com join!, e outra rodada em que só vale a primeira que responder (select!), com um tempo limite (timeout) para a mais lenta.

use std::time::Duration;
use tokio::time::{sleep, timeout};

async fn consultar(fornecedor: &str, ms: u64, preco: u32) -> (String, u32) {
    sleep(Duration::from_millis(ms)).await;
    (fornecedor.to_string(), preco)
}

#[tokio::main]
async fn main() {
    let (a, b, c) = tokio::join!(
        consultar("A", 300, 4750),
        consultar("B", 100, 4990),
        consultar("C", 200, 4500),
    );
    let melhor = [a, b, c].into_iter().min_by_key(|(_, p)| *p).unwrap();
    println!("todas responderam; menor preço: {} ({})", melhor.0, melhor.1);

    tokio::select! {
        r = consultar("rápido", 50, 5000) => println!("primeiro a responder: {}", r.0),
        r = consultar("lento", 500, 4000) => println!("primeiro a responder: {}", r.0),
    }

    match timeout(Duration::from_millis(150), consultar("muito lento", 1000, 3000)).await {

        Err(_) => println!("tempo esgotado: consulta cancelada"),

}

todas responderam; menor preço: C (4500)
primeiro a responder: rápido
tempo esgotado: consulta cancelada

O join! roda as três consultas ao mesmo tempo na mesma tarefa: o tempo total é o da mais lenta (300 ms), e não a soma. O select! espera a primeira que terminar e cancela as outras, simplesmente parando de fazer o poll delas: um future do Rust não faz nada sozinho, só avança quando alguém o aguarda. Por isso o cancelamento é gratuito, e por isso um async fn chamado sem .await não executa nada (o compilador avisa).

Uma macro declarativa

Escreva macro_rules! mapa que crie um HashMap a partir de mapa!{ "a" => 1, "b" => 2 }, aceitando vírgula final, e uma macro contar! que conte quantos argumentos recebeu, em tempo de compilação. Use as duas.

use std::collections::HashMap;

macro_rules! mapa {

        $( m.insert($chave, $valor); )*
        m
    }};
}

macro_rules! contar {
    () => { 0usize };
    ($primeiro:tt $($resto:tt)*) => { 1usize + contar!($($resto)*) };
}

fn main() {

        "Vidas Secas" => 4990,
        "Iracema" => 2500,
    };

    titulos.sort();

Q43

Cargo.toml e Cargo.lock

O que significa serde = "1.0" no Cargo.toml? Por que o Cargo.lock é versionado num executável e, tradicionalmente, não era numa biblioteca?

Uma versão sem operador no Cargo é um requisito compatível (como o ^ do npm): "1.0" aceita qualquer versão >= 1.0.0 e < 2.0.0. O Cargo.lock registra as versões exatas resolvidas, com os checksums, e garante que todos compilam o mesmo código. Num executável, ele é versionado sempre: o que foi testado é o que vai para produção. Numa biblioteca, o lockfile dela é ignorado por quem a usa (vale o do projeto final), e por isso a recomendação antiga era não versioná-lo; desde 2023, a orientação do Cargo é versionar também nas bibliotecas, para que o CI delas seja reprodutível.

Q44

Extractors do Axum

No Axum, um handler como async fn criar(State(db): State<Pool>, Json(novo): Json<NovoLivro>) -> impl IntoResponse não lê a requisição manualmente. Como os parâmetros são preenchidos, e o que acontece quando o JSON do corpo é inválido?

Cada parâmetro é um extractor: um tipo que implementa FromRequestParts ou FromRequest, e o Axum chama a extração de cada um antes de chamar o handler. State entrega o estado compartilhado registrado no roteador; Json<T> lê o corpo, confere o Content-Type e desserializa com o serde; Path, Query e HeaderMap funcionam igual. Se um extractor falha (JSON malformado, campo faltando, tipo errado), o handler nem é chamado, e a resposta de erro do próprio extractor é devolvida (400, 415 ou 422, conforme o caso). O handler recebe dados já validados quanto ao formato e só cuida das regras de negócio.

Q45

O que a macro sqlx::query_as! faz de diferente de uma consulta montada em texto? Qual a exigência dela para compilar?

O query_as!(Livro, "SELECT id, titulo FROM livros WHERE id = $1", id) conecta ao banco na compilação (ou lê um cache gerado com cargo sqlx prepare), pede ao banco que analise o SQL e confere: que a consulta é válida, que as colunas existem, que os tipos delas casam com os campos de Livro e com os parâmetros, e se cada coluna pode ser nula (o que exige Option no campo). Um nome de coluna errado vira erro de compilação, não de execução. E os parâmetros são sempre separados do texto, sem injeção possível. A exigência é ter um banco acessível pela DATABASE_URL no momento da compilação, ou o cache .sqlx/ versionado, que é o que se usa no CI.

Q46

Testes de propriedade

O que é um teste baseado em propriedades (com proptest ou quickcheck), e que propriedade testaria uma função que codifica e decodifica Base64?

Em vez de escrever exemplos (codificar("oi") == "b2k="), descreve-se uma propriedade que deve valer para qualquer entrada, e a ferramenta gera centenas de entradas aleatórias, inclusive casos extremos (vazio, bytes zero, tamanhos que não são múltiplos de 3), procurando um contraexemplo. Quando acha um, ela o reduz (shrinking) ao menor caso que ainda falha. Para Base64, a propriedade central é a ida e volta: decodificar(codificar(bytes)) == bytes para todo bytes; e também que o tamanho da saída é 4 * teto(n / 3) e que ela só tem caracteres do alfabeto. É uma ótima forma de achar os casos de borda que ninguém pensou em escrever.

Q47

Uma API com Axum

Escreva uma API Axum com GET /livros, GET /livros/{id} (404 quando não existe) e POST /livros (201 com o livro criado, ou 422 se o título estiver vazio), guardando os livros num Arc<Mutex<Vec<Livro>>> como estado. Use serde para o JSON.

use axum::{
    Json, Router,
    extract::{Path, State},
    http::StatusCode,
    routing::get,
};
use serde::{Deserialize, Serialize};
use std::sync::{Arc, Mutex};

#[derive(Clone, Serialize)]
struct Livro {
    id: u32,
    titulo: String,
    preco_centavos: u32,
}

#[derive(Deserialize)]
struct NovoLivro {
    titulo: String,
    preco_centavos: u32,
}

type Estado = Arc<Mutex<Vec<Livro>>>;

async fn listar(State(livros): State<Estado>) -> Json<Vec<Livro>> {
    Json(livros.lock().unwrap().clone())
}

async fn buscar(State(livros): State<Estado>, Path(id): Path<u32>) -> Result<Json<Livro>, StatusCode> {
    livros.lock().unwrap().iter().find(|l| l.id == id).cloned().map(Json).ok_or(StatusCode::NOT_FOUND)
}

async fn criar(
    State(livros): State<Estado>,
    Json(novo): Json<NovoLivro>,
) -> Result<(StatusCode, Json<Livro>), (StatusCode, &'static str)> {
    if novo.titulo.trim().is_empty() {
        return Err((StatusCode::UNPROCESSABLE_ENTITY, "título obrigatório"));
    }
    let mut lista = livros.lock().unwrap();
    let livro = Livro { id: lista.len() as u32 + 1, titulo: novo.titulo, preco_centavos: novo.preco_centavos };
    lista.push(livro.clone());
    Ok((StatusCode::CREATED, Json(livro)))
}

#[tokio::main]
async fn main() {
    let estado: Estado = Arc::new(Mutex::new(Vec::new()));
    let app = Router::new()
        .route("/livros", get(listar).post(criar))
        .route("/livros/{id}", get(buscar))
        .with_state(estado);
    let ouvinte = tokio::net::TcpListener::bind("127.0.0.1:3000").await.unwrap();
    axum::serve(ouvinte, app).await.unwrap();
}

struct Xorshift(u64);

impl Xorshift {
    fn proximo(&mut self) -> u64 {
        self.0 ^= self.0 << 13;
        self.0 ^= self.0 >> 7;
        self.0 ^= self.0 << 17;
        self.0
    }
}

fn codificar_rle(s: &str) -> String {
    let mut saida = String::new();
    let mut chars = s.chars().peekable();
    while let Some(c) = chars.next() {
        let mut n = 1;
        while chars.peek() == Some(&c) {
            chars.next();
            n += 1;
        }
        saida.push_str(&format!("{n}{c}"));
    }
    saida
}

fn decodificar_rle(s: &str) -> String {
    let mut saida = String::new();
    let mut n = 0;
    for c in s.chars() {
        if let Some(d) = c.to_digit(10) {
            n = n * 10 + d as usize;
        } else {
            saida.push_str(&c.to_string().repeat(n));
            n = 0;
        }
    }
    saida
}

fn main() {
    let mut rng = Xorshift(2026);
    let mut falhas = 0;
    for _ in 0..1000 {
        let tamanho = (rng.proximo() % 30) as usize;
        let texto: String = (0..tamanho).map(|_| ['a', 'b', 'c'][(rng.proximo() % 3) as usize]).collect();
        if decodificar_rle(&codificar_rle(&texto)) != texto {
            falhas += 1;
        }
    }
    println!("1000 textos de a, b e c: {falhas} falha(s)");
    println!("exemplo: {:?} -> {:?}", "aaabccccccccccccd", codificar_rle("aaabccccccccccccd"));

    let com_digito = "a11";
    let ida_e_volta = decodificar_rle(&codificar_rle(com_digito));
    println!("com dígitos: {com_digito:?} -> {:?} -> {ida_e_volta:?}", codificar_rle(com_digito));
}

Q49

Quando unsafe

O que um bloco unsafe permite que o Rust seguro não permite? Ele desliga o borrow checker? Qual a responsabilidade de quem escreve uma função segura que usa unsafe por dentro?

O unsafe libera cinco operações: desreferenciar ponteiros crus, chamar funções unsafe (inclusive as de FFI), acessar ou alterar variáveis static mut, implementar traits unsafe (como Send e Sync à mão) e acessar campos de union. Ele não desliga o borrow checker nem as outras verificações: referências comuns continuam verificadas dentro do bloco. Quem escreve uma função segura que usa unsafe por dentro garante que nenhuma forma de chamá-la, com quaisquer argumentos válidos, causa comportamento indefinido: a função é uma fronteira, e a responsabilidade é de quem a escreve, não de quem chama. Por isso o costume é um comentário // SAFETY: explicando por que cada bloco está correto, e manter os blocos pequenos e encapsulados.

Q50

no_std

O que muda num programa #![no_std] para um microcontrolador? O que deixa de existir, e o que continua disponível?

Sem o sistema operacional, deixa de existir a biblioteca std, que depende dele: alocação no heap (Vec, String, Box), arquivos, threads, rede, println!. Continua disponível a core: tipos primitivos, Option, Result, iteradores, traits, slice, formatação (sem destino de saída) e as operações atômicas. Com um alocador fornecido, volta também a alloc (Vec, String, Box). O programa precisa definir o próprio #[panic_handler] (o que fazer num pânico: parar, reiniciar, piscar um LED) e o ponto de entrada (com o cortex-m-rt, #[entry]). O borrow checker e o sistema de tipos continuam valendo, e é isso que torna o Rust atraente para embarcados: os registradores de periféricos viram tipos que só podem ser usados do jeito certo.

Q51

Um protocolo sobre TCP

Por que um servidor TCP não pode assumir que um read traz uma mensagem completa? Que duas formas de delimitar mensagens são comuns?

O TCP entrega um fluxo de bytes, sem fronteiras: uma mensagem pode chegar partida em vários read, e duas mensagens podem chegar juntas num só. O protocolo da aplicação é que define onde cada mensagem termina. As duas formas comuns são: um delimitador (uma quebra de linha, como em HTTP/1, SMTP e Redis em parte), lido com um BufReader e read_line; ou um prefixo de tamanho (os primeiros 4 bytes dizem quantos vêm a seguir, como no gRPC e em muitos protocolos binários), lido com read_exact. O delimitador é simples e legível; o prefixo de tamanho suporta dados binários arbitrários e permite alocar o buffer certo de uma vez (com um limite máximo, para não aceitar um "tamanho" de 4 GB enviado por um atacante).

Q52

Medir antes de otimizar

Que ferramentas o curso usa para achar o gargalo de um programa Rust lento, e por que olhar o código e "adivinhar" costuma falhar?

Primeiro, compilar em release (cargo build --release): a diferença para o debug chega a dezenas de vezes, e muitos "problemas de desempenho" são só isso. Depois, medir: o criterion para comparar versões de uma função com estatística (aquecimento, várias amostras, detecção de regressão), e um profiler de amostragem (perf com o cargo flamegraph) para ver onde o tempo realmente vai, num gráfico de chamas. Adivinhar falha porque a intuição aponta para o código "complicado", enquanto o tempo costuma estar em lugares inesperados: alocações repetidas num laço, uma cópia de String escondida num clone(), um HashMap com o hasher padrão (seguro contra ataques, mas não o mais rápido) ou E/S sem buffer.

use std::error::Error;
use std::fs::File;
use std::io::{BufRead, BufReader, BufWriter, Write};
use std::process::Command;

fn main() -> Result<(), Box<dyn Error>> {
    {
        let mut saida = BufWriter::new(File::create("dados.txt")?);

Q54

Um servidor TCP de eco por linhas

Com std::net, suba um servidor TCP numa porta escolhida pelo sistema (127.0.0.1:0), que atenda cada conexão numa thread e responda cada linha recebida em maiúsculas, encerrando a conexão com a linha sair. No mesmo programa, conecte dois clientes e mostre as respostas.

use std::io::{BufRead, BufReader, Write};
use std::net::{TcpListener, TcpStream};
use std::thread;

fn atender(conexao: TcpStream) -> std::io::Result<()> {
    let mut escrita = conexao.try_clone()?;
    for linha in BufReader::new(conexao).lines() {
        let linha = linha?;
        if linha == "sair" {
            writeln!(escrita, "até mais")?;
            break;
        }
        writeln!(escrita, "{}", linha.to_uppercase())?;
    }
    Ok(())
}

fn cliente(endereco: std::net::SocketAddr, nome: &str, mensagens: &[&str]) -> std::io::Result<Vec<String>> {
    let mut conexao = TcpStream::connect(endereco)?;
    for m in mensagens {
        writeln!(conexao, "{m}")?;
    }
    writeln!(conexao, "sair")?;
    let respostas = BufReader::new(conexao).lines().collect::<Result<Vec<_>, _>>()?;
    Ok(respostas.into_iter().map(|r| format!("[{nome}] {r}")).collect())
}

fn main() -> std::io::Result<()> {
    let ouvinte = TcpListener::bind("127.0.0.1:0")?;
    let endereco = ouvinte.local_addr()?;
    thread::spawn(move || {
        for conexao in ouvinte.incoming().flatten() {
            thread::spawn(move || atender(conexao));
        }
    });

    for r in cliente(endereco, "ana", &["olá, servidor", "ação"])? {
        println!("{r}");
    }
    for r in cliente(endereco, "bruno", &["rust"])? {
        println!("{r}");
    }
    Ok(())
}
[ana] OLÁ, SERVIDOR
[ana] AÇÃO
[ana] até mais
[bruno] RUST
[bruno] até mais

A porta 0 pede ao sistema uma porta livre, e o local_addr() diz qual foi: o exemplo nunca colide com outro programa. O to_uppercase do Rust trata Unicode corretamente ("ação" vira "AÇÃO"), ao contrário do strtoupper do PHP visto no outro caderno. O protocolo é delimitado por linha, e o BufReader cuida de juntar os pedaços que o TCP entregar. Uma thread por conexão é simples e funciona bem para dezenas de clientes; para milhares, o caminho é o tokio, com uma tarefa por conexão.

Q55

split_at_mut com unsafe

A biblioteca padrão implementa split_at_mut, que divide um slice mutável em duas partes mutáveis. Escreva a sua versão, dividir_mut(v: &mut [i32], meio: usize) -> (&mut [i32], &mut [i32]), mostrando por que a versão segura não compila (em comentário) e usando unsafe com ponteiros crus e um comentário SAFETY. Use-a para alterar as duas metades.

fn dividir_mut(v: &mut [i32], meio: usize) -> (&mut [i32], &mut [i32]) {
    let len = v.len();
    assert!(meio <= len, "meio fora do slice");
    // Versão segura, recusada: dois empréstimos mutáveis do mesmo v ao mesmo tempo.
    // (&mut v[..meio], &mut v[meio..])
    let p = v.as_mut_ptr();
    // SAFETY: as faixas [0, meio) e [meio, len) não se sobrepõem, ficam dentro do slice
    // (garantido pelo assert) e herdam o lifetime de v, então ninguém mais acessa esses
    // elementos enquanto as duas fatias existirem.
    unsafe { (std::slice::from_raw_parts_mut(p, meio), std::slice::from_raw_parts_mut(p.add(meio), len - meio)) }
}

fn main() {
    let mut v = [1, 2, 3, 4, 5, 6];
    let (esq, dir) = dividir_mut(&mut v, 2);
    esq[0] = 100;
    dir.iter_mut().for_each(|x| *x *= 10);
    println!("{v:?}");
}
[100, 2, 30, 40, 50, 60]

O compilador recusa a versão segura porque não sabe que as duas faixas são disjuntas: para ele, são dois empréstimos mutáveis do mesmo v. O programador sabe, e o unsafe é a forma de afirmar isso, ficando responsável pela prova. O assert! é parte essencial da segurança: sem ele, um meio maior que o tamanho criaria fatias fora do array, e a função "segura" causaria comportamento indefinido. A ferramenta cargo miri executa o código num interpretador que detecta essas violações e é o teste certo para todo código unsafe.

Q56

Chamando C com FFI

Declare as funções strlen e abs da biblioteca C num bloco unsafe extern "C" (a sintaxe da edição 2024) e chame-as a partir do Rust, convertendo uma &str com CString. Mostre o que acontece ao tentar criar uma CString com um \0 no meio.

use std::ffi::{CString, c_char, c_int};

unsafe extern "C" {
    fn strlen(s: *const c_char) -> usize;
    safe fn abs(x: c_int) -> c_int; // declarada segura: não recebe ponteiro, não há como usá-la errado
}

fn main() {
    let texto = "ação";
    let c = CString::new(texto).expect("sem \\0 no meio");
    // SAFETY: c é uma string C válida, terminada em \0, e vive até o fim da chamada.
    let n = unsafe { strlen(c.as_ptr()) };
    println!("strlen(\"{texto}\") = {n} bytes; chars = {}", texto.chars().count());
    println!("abs(-42) = {}", abs(-42));

    match CString::new("meio\0quebrado") {
        Ok(_) => println!("aceitou"),
        Err(e) => println!("recusado: \\0 na posição {}", e.nul_position()),
    }
}

recusado: \0 na posição 4

Cada item pode então ser marcado safe quando chamá-lo nunca é perigoso, como o abs. A CString garante o terminador \0 e recusa um \0 no meio, que faria o C enxergar uma string mais curta. O strlen conta bytes: os mesmos 6 de "ação" que o caderno de C# mostrou.

Padrões que mudam em Rust

Por que alguns padrões clássicos da orientação a objetos mudam de forma em Rust? Dê o exemplo do Builder e do State (typestate).

O Rust não tem herança de implementação, nem null, e tem um sistema de tipos forte com posse: muitos padrões que existem para contornar limitações de outras linguagens ficam diferentes ou desnecessários. Q58

Features no Cargo

O que são features no Cargo.toml, e por que elas devem ser aditivas? Dê um exemplo de feature bem e mal projetada.

São opções de compilação nomeadas: [features] json = ["dep:serde_json"] liga uma dependência opcional e o código marcado com #[cfg(feature = "json")]. O Cargo unifica as features: se duas dependências do seu projeto usam a mesma crate, uma com json e outra sem, ela é compilada uma vez, com a união das duas. Por isso uma feature só pode acrescentar funcionalidade, nunca remover nem mudar o comportamento de algo que já existe. Bem projetada: json, que acrescenta funções de serialização. Mal projetada: sem-std (que remove coisas) ou algoritmo-rapido que troca o resultado de uma função existente; ligada por uma dependência distante, ela quebraria outra parte do programa que contava com o comportamento padrão.

Q59

Documentação que não mente

O que são os doc tests, e por que eles evitam que a documentação fique desatualizada?

Os exemplos em blocos de código dentro dos comentários de documentação (///) são compilados e executados pelo cargo test, como testes. Se a API muda e o exemplo deixa de compilar ou de produzir o resultado afirmado num assert_eq!, o teste falha. A documentação passa a ter a mesma garantia que o código: um exemplo errado é um teste vermelho. Linhas que começam com # ficam ocultas na documentação renderizada, mas são compiladas, o que permite esconder a preparação (os use, a criação de objetos) e mostrar só o essencial. Q61

Uma CLI sem dependências

Escreva o núcleo de uma ferramenta de linha de comando que conte linhas, palavras e bytes (como o wc), com as opções -l, -w, -c e --help, analisando os argumentos com um match sobre slices e devolvendo Result para opções inválidas. Para o exemplo ser reprodutível, passe os argumentos como um vetor e o texto como uma string.

#[derive(Debug, Default)]
struct Opcoes {
    linhas: bool,
    palavras: bool,
    bytes: bool,
}

fn analisar(args: &[&str]) -> Result<Option<Opcoes>, String> {
    let mut o = Opcoes::default();
    for a in args {
        match *a {
            "-l" => o.linhas = true,
            "-w" => o.palavras = true,
            "-c" => o.bytes = true,
            "-h" | "--help" => return Ok(None),
            outro => return Err(format!("opção desconhecida: {outro} (use --help)")),
        }
    }
    if !(o.linhas || o.palavras || o.bytes) {
        o = Opcoes { linhas: true, palavras: true, bytes: true }; // sem opções: tudo, como o wc
    }
    Ok(Some(o))
}

fn contar(texto: &str, o: &Opcoes) -> String {
    let mut partes = vec![];
    if o.linhas {
        partes.push(texto.lines().count().to_string());
    }
    if o.palavras {
        partes.push(texto.split_whitespace().count().to_string());
    }
    if o.bytes {
        partes.push(texto.len().to_string());
    }
    partes.join(" ")
}

fn main() {
    let texto = "o rato roeu\na roupa do rei\nde Roma\n";
    for args in [vec![], vec!["-l"], vec!["-w", "-c"], vec!["-x"], vec!["--help"]] {
        let rotulo = format!("wc {}", args.join(" "));
        match analisar(&args) {
            Ok(Some(o)) => println!("{rotulo:<10} -> {}", contar(texto, &o)),
            Ok(None) => println!("{rotulo:<10} -> uso: wc [-l] [-w] [-c]"),
            Err(e) => println!("{rotulo:<10} -> erro: {e}"),
        }
    }
}
wc         -> 3 9 35
wc -l      -> 3
wc -w -c   -> 9 35
wc -x      -> erro: opção desconhecida: -x (use --help)
wc --help  -> uso: wc [-l] [-w] [-c]

Num programa de verdade, os argumentos vêm de std::env::args().skip(1), o texto da entrada padrão ou de arquivos, e o erro sai pela saída de erro com std::process::exit(2). Para ferramentas maiores, o clap (com #[derive(Parser)]) gera tudo isso a partir de um struct, incluindo a ajuda, a validação e o autocompletar do terminal. Separar analisar e contar da E/S é o que permite testar o núcleo sem processos nem arquivos, como a calculadora dos desafios.

Q62

ECS no Bevy

O Bevy organiza os jogos com ECS. Como um sistema do Bevy declara os dados de que precisa, e por que isso permite ao motor rodar sistemas em paralelo com segurança?

Um sistema é uma função comum cujos parâmetros dizem o que ela acessa: fn mover(mut q: Query<(&mut Transform, &Velocidade)>, tempo: Res<Time>) pede, para cada entidade com Transform e Velocidade, acesso mutável ao primeiro e de leitura ao segundo, além do recurso global Time. Como esse acesso está na assinatura, o agendador do Bevy sabe, antes de rodar, quais sistemas leem e escrevem quais componentes. Dois sistemas que só leem Velocidade, ou que mexem em componentes diferentes, rodam em paralelo; dois que escrevem no mesmo componente rodam em sequência. São as regras de empréstimo do Rust aplicadas ao agendamento: a corrida de dados entre sistemas fica impossível sem nenhuma trava manual.

Q63

Consenso

Num sistema distribuído com três réplicas de um banco, por que é preciso um algoritmo de consenso como o Raft? O que acontece quando a rede separa uma réplica das outras duas?

Sem consenso, cada réplica poderia aceitar escritas diferentes, e o sistema teria versões conflitantes do mesmo dado. O Raft elege um líder, que recebe todas as escritas e as replica; uma escrita só é confirmada quando a maioria (2 de 3) a gravou. Quando a rede separa uma réplica, o lado com duas réplicas continua tendo maioria: elege ou mantém o líder e segue funcionando. A réplica isolada não consegue maioria, não confirma escritas (e, se era o líder, deixa de ser) e fica parada até a rede voltar, quando recebe o que perdeu. É a troca do teorema CAP: diante de uma partição, o Raft escolhe consistência em vez de disponibilidade no lado minoritário. É também por isso que os grupos têm tamanho ímpar: com 4 réplicas, uma partição de 2 e 2 deixa os dois lados sem maioria.

Q64

Fuzzing

O que é fuzzing, e por que ele encontra bugs em código Rust "seguro"? Que tipo de função é a melhor candidata?

Fuzzing é executar uma função milhões de vezes com entradas geradas automaticamente, guiado pela cobertura: o fuzzer (como o cargo fuzz, sobre o libFuzzer) muta as entradas que exercitam caminhos novos do código, procurando uma que cause pânico, estouro, laço infinito ou consumo excessivo de memória. O Rust seguro impede o comportamento indefinido, mas não impede o pânico (um índice fora dos limites, um unwrap num None, um estouro em debug) nem os erros de lógica, e um pânico num servidor é uma negação de serviço. As melhores candidatas são as funções que recebem dados não confiáveis: parsers de formatos de arquivo, de protocolos de rede, de imagens, de configuração. São exatamente as que um atacante alimenta.

Q65

Como o Rust evolui

O que são as edições do Rust (2018, 2021, 2024), e como elas permitem mudar a linguagem sem quebrar o código existente? Qual o papel das RFCs?

Uma edição é um conjunto de mudanças incompatíveis que cada crate adota quando quiser, declarando edition = "2024" no Cargo.toml. Crates de edições diferentes compilam juntas no mesmo projeto, porque a edição afeta só a análise do código de cada uma; o compilador entende todas. Assim o Rust pôde, por exemplo, transformar async em palavra reservada e exigir unsafe extern sem quebrar nenhuma biblioteca antiga. O cargo fix --edition migra a maior parte do código sozinho. As RFCs (Requests for Comments) são o processo público de proposta: qualquer mudança relevante na linguagem, na biblioteca ou no Cargo é escrita, discutida abertamente e aprovada pela equipe responsável antes de ser implementada, e geralmente passa um tempo como recurso instável, disponível só no compilador nightly.

Q66

Uma cadeia de blocos com hash

Para entender a ideia por trás de um blockchain, monte uma cadeia de blocos em que cada bloco guarda os dados e o hash do anterior, calculado com o DefaultHasher da biblioteca padrão (que não é criptográfico: serve só para o exemplo). Escreva valida(&cadeia) -> Result<(), usize> e mostre que alterar um bloco do meio invalida a cadeia a partir dele.

use std::collections::hash_map::DefaultHasher;
use std::hash::{Hash, Hasher};

#[derive(Hash, Clone)]
struct Bloco {
    indice: u32,
    dados: String,
    hash_anterior: u64,
}

fn hash_de(b: &Bloco) -> u64 {
    let mut h = DefaultHasher::new();
    b.hash(&mut h);
    h.finish()
}

fn encadear(dados: &[&str]) -> Vec<Bloco> {
    let mut cadeia: Vec<Bloco> = vec![];
    for (i, d) in dados.iter().enumerate() {
        let anterior = cadeia.last().map(hash_de).unwrap_or(0);
        cadeia.push(Bloco { indice: i as u32, dados: d.to_string(), hash_anterior: anterior });
    }
    cadeia
}

fn valida(cadeia: &[Bloco]) -> Result<(), usize> {
    for par in cadeia.windows(2) {
        if par[1].hash_anterior != hash_de(&par[0]) {
            return Err(par[1].indice as usize);
        }
    }
    Ok(())
}

fn main() {
    let mut cadeia = encadear(&["Ana paga 10 a Bruno", "Bruno paga 3 a Carla", "Carla paga 1 a Ana", "Ana paga 2 a Bruno"]);
    println!("cadeia original: {:?}", valida(&cadeia));

    cadeia[1].dados = "Bruno paga 300 a Carla".into(); // adulteração
    match valida(&cadeia) {
        Ok(()) => println!("adulterada: passou?!"),
        Err(i) => println!("adulterada: quebra no bloco {i}, que não reconhece o anterior"),
    }

    let refeita = encadear(&cadeia.iter().map(|b| b.dados.as_str()).collect::<Vec<_>>());
    println!("recalculando todos os hashes: {:?}", valida(&refeita));
}

adulterada: quebra no bloco 2, que não reconhece o anterior

Alterar o bloco 1 muda o hash dele, e o bloco 2, que guardava o hash antigo, deixa de reconhecê-lo. O atacante pode recalcular todos os hashes seguintes, como a última linha mostra; o que impede isso num blockchain real é a prova de trabalho (cada bloco exige um cálculo caro) ou de participação, somada a uma rede de participantes que mantém cópias e só aceita a cadeia com mais trabalho acumulado. O DefaultHasher também muda entre versões do Rust e não resiste a ataques: o caso real usa SHA-256 (sha2) ou BLAKE3.

Q67

Um interpretador de expressões

Escreva um analisador de expressões aritméticas com precedência e parênteses, por descida recursiva: um tokenizer e as funções expressao (soma e subtração), termo (multiplicação e divisão) e fator (número, negativo ou parênteses), que devolvem Result<f64, String>. Avalie quatro expressões, uma com erro.

#[derive(Debug, Clone, Copy, PartialEq)]
enum Token {
    Num(f64),
    Op(char),
}

fn tokenizar(s: &str) -> Result<Vec<Token>, String> {
    let mut tokens = vec![];
    let cs: Vec<char> = s.chars().collect();
    let mut i = 0;
    while i < cs.len() {
        let c = cs[i];
        if c.is_whitespace() {
            i += 1;
        } else if c.is_ascii_digit() || c == '.' {
            let ini = i;
            while i < cs.len() && (cs[i].is_ascii_digit() || cs[i] == '.') {
                i += 1;
            }
            let texto: String = cs[ini..i].iter().collect();
            tokens.push(Token::Num(texto.parse().map_err(|_| format!("número inválido: {texto}"))?));
        } else if "+-*/()".contains(c) {
            tokens.push(Token::Op(c));
            i += 1;
        } else {
            return Err(format!("caractere inesperado: {c}"));
        }
    }
    Ok(tokens)
}

struct Analisador {
    tokens: Vec<Token>,
    pos: usize,
}

impl Analisador {
    fn espiar(&self) -> Option<Token> {
        self.tokens.get(self.pos).copied()
    }
    fn expressao(&mut self) -> Result<f64, String> {
        let mut v = self.termo()?;
        while let Some(Token::Op(op @ ('+' | '-'))) = self.espiar() {
            self.pos += 1;
            let d = self.termo()?;
            v = if op == '+' { v + d } else { v - d };
        }
        Ok(v)
    }
    fn termo(&mut self) -> Result<f64, String> {
        let mut v = self.fator()?;
        while let Some(Token::Op(op @ ('*' | '/'))) = self.espiar() {
            self.pos += 1;
            let d = self.fator()?;
            if op == '/' && d == 0.0 {
                return Err("divisão por zero".into());
            }
            v = if op == '*' { v * d } else { v / d };
        }
        Ok(v)
    }
    fn fator(&mut self) -> Result<f64, String> {
        self.pos += 1;
        match self.tokens.get(self.pos - 1).copied() {
            Some(Token::Num(n)) => Ok(n),
            Some(Token::Op('-')) => Ok(-self.fator()?),
            Some(Token::Op('(')) => {
                let v = self.expressao()?;
                if self.espiar() != Some(Token::Op(')')) {
                    return Err("faltou fechar o parêntese".into());
                }
                self.pos += 1;
                Ok(v)
            }
            outro => Err(format!("esperava um número, achei {outro:?}")),
        }
    }
}

fn avaliar(s: &str) -> Result<f64, String> {
    let mut a = Analisador { tokens: tokenizar(s)?, pos: 0 };
    let v = a.expressao()?;
    match a.espiar() {
        None => Ok(v),
        Some(t) => Err(format!("sobrou {t:?} no fim")),
    }
}

fn main() {
    for e in ["2 + 3 * 4", "(2 + 3) * 4", "-(1.5 + 2) * -2", "2 * (3 + ", "7 / (2 - 2)"] {
        match avaliar(e) {
            Ok(v) => println!("{e:<18} = {v}"),
            Err(m) => println!("{e:<18} -> erro: {m}"),
        }
    }
}

A precedência sai da estrutura das funções: expressao chama termo, que chama fator, e por isso a multiplicação é resolvida antes da soma sem nenhuma tabela. Cada regra da gramática vira uma função, o que torna a descida recursiva o jeito mais simples de escrever um parser à mão; é a base do interpretador construído no artigo #45. O padrão op @ ('+' | '-') casa com um dos dois caracteres e dá nome a ele. Para gramáticas maiores, as bibliotecas nom e pest do módulo 9 geram a mesma estrutura com menos código.

D1

Uma calculadora de terminal

Escreva uma calculadora de terminal com sete operações: soma, subtração, multiplicação, divisão, potência (expoente inteiro), porcentagem (15 % 200 é 15% de 200) e raiz quadrada (raiz 2). Ela deve: (a) aceitar vírgula ou ponto como separador decimal; (b) guardar o último resultado em ans, utilizável na conta seguinte; (c) recusar divisão por zero, raiz de negativo, expoente fracionário, resultado infinito e texto que não é número com uma mensagem clara, sem encerrar o programa; (d) ter os comandos hist (histórico) e sair. Separe o núcleo (um módulo calc, sem E/S, com um enum de erros e Result) da interface (main), e escreva testes para o núcleo.

Caminho da solução

  • Núcleo: o módulo calc tem a struct Calculadora com o ans e o método avaliar(&mut self, linha: &str) -> Result<f64, ErroCalc>. O ErroCalc é um enum com uma variante por tipo de erro e implementa Display; nenhuma String de erro solta, e o match da interface não pode esquecer um caso.
  • Números: str::parse::<f64>() depois de trocar a vírgula por ponto, recusando inf e NaN escritos por extenso (o parse os aceita). O resultado é conferido com is_finite.
  • Interface: stdin().lines(), um Vec<String> de histórico e a vírgula decimal na exibição.
  • Testes: um #[cfg(test)] mod tests dentro do módulo, rodado com cargo test (ou rustc --test).
mod calc {
    use std::fmt;

    #[derive(Debug, PartialEq)]
    pub enum ErroCalc {
        Formato,
        Numero(String),
        Operacao(String),
        DivisaoPorZero,
        RaizNegativa,
        Expoente,
        Estouro,
    }

    impl fmt::Display for ErroCalc {
        fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
            match self {
                ErroCalc::Formato => write!(f, "use \"a op b\" ou \"raiz a\""),
                ErroCalc::Numero(t) => write!(f, "\"{t}\" não é um número"),
                ErroCalc::Operacao(op) => write!(f, "operação desconhecida \"{op}\" (use + - * / ^ % ou raiz)"),
                ErroCalc::DivisaoPorZero => write!(f, "divisão por zero"),
                ErroCalc::RaizNegativa => write!(f, "raiz de número negativo"),
                ErroCalc::Expoente => write!(f, "o expoente precisa ser inteiro"),
                ErroCalc::Estouro => write!(f, "resultado grande demais"),
            }
        }
    }

    #[derive(Default)]
    pub struct Calculadora {
        ans: f64,
    }

    impl Calculadora {
        fn numero(&self, t: &str) -> Result<f64, ErroCalc> {
            if t == "ans" {
                return Ok(self.ans);
            }
            let ok = t.chars().all(|c| c.is_ascii_digit() || matches!(c, ',' | '.' | '-'));
            match t.replace(',', ".").parse::<f64>() {
                Ok(v) if ok => Ok(v),
                _ => Err(ErroCalc::Numero(t.to_string())), // recusa "inf", "NaN" e texto
            }
        }

        pub fn avaliar(&mut self, linha: &str) -> Result<f64, ErroCalc> {
            let p: Vec<&str> = linha.split_whitespace().collect();
            let r = match p.as_slice() {
                ["raiz", x] => {
                    let x = self.numero(x)?;
                    if x < 0.0 { return Err(ErroCalc::RaizNegativa) }
                    x.sqrt()
                }
                [a, op, b] => {
                    let (a, b) = (self.numero(a)?, self.numero(b)?);
                    match *op {
                        "+" => a + b,
                        "-" => a - b,
                        "*" => a * b,
                        "/" if b == 0.0 => return Err(ErroCalc::DivisaoPorZero),
                        "/" => a / b,
                        "%" => a * b / 100.0,
                        "^" if b.fract() != 0.0 => return Err(ErroCalc::Expoente),
                        "^" => a.powi(b as i32),
                        outro => return Err(ErroCalc::Operacao(outro.to_string())),
                    }
                }
                _ => return Err(ErroCalc::Formato),
            };
            if !r.is_finite() {
                return Err(ErroCalc::Estouro);
            }
            self.ans = r; // só um resultado válido substitui o ans
            Ok(r)
        }
    }

    #[cfg(test)]
    mod tests {
        use super::*;

        #[test]
        fn usa_o_ans() {
            let mut c = Calculadora::default();
            c.avaliar("2 + 3").unwrap();
            assert_eq!(c.avaliar("ans * 2"), Ok(10.0));
        }

        #[test]
        fn erro_nao_altera_o_ans() {
            let mut c = Calculadora::default();
            c.avaliar("4 * 2").unwrap();
            assert_eq!(c.avaliar("1 / 0"), Err(ErroCalc::DivisaoPorZero));
            assert_eq!(c.avaliar("ans + 0"), Ok(8.0));
        }
    }
}

Um servidor chave-valor concorrente

Escreva um servidor TCP que guarde pares chave-valor em memória, com os comandos de texto SET chave valor, GET chave, DEL chave e KEYS, uma linha por comando, atendendo vários clientes ao mesmo tempo. Acrescente expiração opcional (SET chave valor EX 10), persistência num arquivo de log e testes de integração que conectem clientes reais.

Caminho da solução

  • Protocolo: uma linha por comando e uma por resposta (OK, o valor, (nil) ou ERR mensagem), como uma versão mínima do Redis. A análise do comando é uma função pura fn analisar(linha: &str) -> Result<Comando, String>, com um enum Comando, testável sem rede.
  • Concorrência: com std, um Arc<RwLock<HashMap<String, Entrada>>> e uma thread por conexão (o servidor de eco do módulo 9); com tokio, uma tarefa por conexão. O RwLock permite muitos GET em paralelo e um SET por vez. Para escalar, o mapa pode ser dividido em vários pedaços (shards), cada um com a sua trava.
  • Expiração: cada Entrada guarda o valor e um Option<Instant>. O GET verifica e apaga o que expirou (expiração preguiçosa), e uma thread de fundo varre o mapa de tempos em tempos para não acumular chaves esquecidas.
  • Persistência: cada SET e DEL é acrescentado a um arquivo (com BufWriter e flush a cada comando, ou a cada segundo, uma troca entre segurança e velocidade); ao iniciar, o servidor relê o log. Uma compactação reescreve o log só com o estado atual, num arquivo temporário trocado com rename.
  • Testes: testes unitários do analisar e da expiração (com o tempo injetado, não com sleep), e testes de integração que sobem o servidor na porta 0, conectam dois clientes e verificam que o SET de um aparece no GET do outro.

É a mesma ideia do banco chave-valor do caderno de C++, agora com concorrência: o compilador garante que nenhuma thread lê o mapa enquanto outra o altera sem passar pela trava.
