Q1

Do código ao processo

Descreva o caminho de um Program.cs até a execução: o que o compilador gera, o que é IL e o que o JIT faz. Por que o mesmo .dll roda em Windows, Linux e macOS?

O compilador do C# (Roslyn) não gera código de máquina: gera IL (Intermediate Language), um código para uma máquina virtual, guardado num assembly (.dll) junto com os metadados dos tipos. Ao executar, o runtime (CLR) carrega o assembly e o JIT (just-in-time) traduz cada método para o código de máquina do processador na primeira vez em que ele é chamado. Como o IL não depende do processador nem do sistema, o mesmo .dll roda em qualquer plataforma que tenha o runtime do .NET; só o executável de partida (o apphost) é específico. O Native AOT, visto no fim do curso, faz o caminho inverso: compila tudo para código de máquina antes, sem JIT.

Q2

Tipos de valor e de referência

Qual a diferença entre int (tipo de valor) e string ou uma class (tipos de referência) numa atribuição b = a? Por que a string, sendo de referência, se comporta "como valor"?

Num tipo de valor, a variável contém o próprio dado: b = a copia o valor, e as duas variáveis seguem independentes. Num tipo de referência, a variável contém uma referência para um objeto no heap: b = a copia a referência, e as duas passam a apontar para o mesmo objeto; alterar o objeto por b aparece em a. A string é de referência, mas é imutável: nenhum método a altera; ToUpper, Replace e + criam strings novas. Como ninguém consegue mudar o objeto compartilhado, compartilhá-lo é indistinguível de copiá-lo.

Q3

decimal, double e dinheiro

Por que 0.1 + 0.2 == 0.3 é falso com double e verdadeiro com decimal? Qual usar para preços na livraria do curso, e qual o custo?

O double guarda números em binário (IEEE 754), e 0,1 não tem representação binária finita, assim como 1/3 não tem em decimal: o valor guardado é o mais próximo possível, e os erros se somam. O decimal guarda um inteiro de 96 bits e uma escala decimal, então 0,1 é exatamente 1 × 10⁻¹. Para dinheiro, use decimal: centavos não podem sumir num arredondamento. O custo é desempenho (as contas são feitas em software, muitas vezes mais lentas) e alcance menor (cerca de 7,9 × 10²⁸, contra 1,8 × 10³⁰⁸ do double). Para física, gráficos e estatística, double.

Q4

Parse ou TryParse

Qual a diferença entre int.Parse(texto) e int.TryParse(texto, out int n)? Qual usar para ler o que o usuário digitou, e por quê?

O Parse lança FormatException (ou OverflowException) quando o texto não é um número; o TryParse devolve false e deixa n com 0, sem exceção. Para entrada do usuário, use TryParse: digitar errado é esperado, não excepcional, e um if deixa o fluxo mais claro e mais barato que um try/catch. O Parse cabe onde um texto inválido é de fato um erro de programa, como um valor de configuração que deveria estar sempre correto. Os dois aceitam um IFormatProvider: double.Parse("1,5") depende da cultura da máquina; para formato fixo, use CultureInfo.InvariantCulture.

Q5

ref, out e in

Explique a diferença entre os modificadores de parâmetro ref, out e in. Por que o C# exige escrever ref também na chamada?

  • **ref**: passa a própria variável (por referência). Ela precisa estar inicializada antes, e o método pode ler e alterar.
  • **out: também por referência, mas para saída: não precisa estar inicializada, e o método é obrigado** a atribuir antes de retornar (como no TryParse).
  • **in: por referência e somente leitura**; serve para evitar a cópia de structs grandes.

Exigir o modificador na chamada (Trocar(ref a, ref b)) deixa visível, no ponto de uso, que a variável pode mudar. É a resposta do C# ao problema das referências escondidas que o C++ tem.

Q6

List, array ou Dictionary

Para cada caso, escolha entre T[], List<T> e Dictionary<TKey, TValue>: (a) as notas de um aluno numa prova com 10 questões; (b) os itens de um carrinho de compras; (c) buscar um livro pelo ISBN.

  • (a) Array: o tamanho é fixo e conhecido (10).
  • (b) **List<T>**: itens entram e saem; a lista cresce sozinha.
  • (c) **Dictionary<string, Livro>**: busca pela chave em O(1) em média. Procurar o ISBN numa lista seria percorrê-la inteira a cada busca, em O(n).
Q7

Quando capturar uma exceção

"Capture apenas as exceções que você sabe tratar." Explique a regra e por que catch (Exception) { } vazio é um dos piores trechos que um programa pode ter.

Capturar uma exceção é afirmar que, naquele ponto, existe uma ação útil: tentar de novo, usar um valor padrão, avisar o usuário. Se não há, a exceção deve subir até um nível que saiba o que fazer, que no pior caso registra o erro e encerra. O catch (Exception) { } vazio engole qualquer erro, inclusive bugs (NullReferenceException, IndexOutOfRangeException): o programa segue num estado inconsistente, e o problema reaparece depois, longe da causa e sem nenhum rastro. Se for preciso registrar e repassar, use throw; (sem argumento), que preserva o stack trace original; throw ex; o reinicia.

switch moderno

Escreva static string Classificar(int idade) usando uma expressão switch com padrões relacionais (< 0, < 13, < 18, < 60, _), devolvendo "inválida", "criança", "adolescente", "adulto" ou "idoso". {
    < 0 => "inválida",
    < 13 => "criança",
    < 18 => "adolescente",
    < 60 => "adulto",
    _ => "idoso",

{

Q11

Métodos com parâmetros opcionais e out

Escreva static bool TentarDividir(int a, int b, out int quociente, out int resto) e static string Repetir(string texto, int vezes = 2, string separador = " "). Chame o segundo com argumentos nomeados, pulando um dos opcionais.

static bool TentarDividir(int a, int b, out int quociente, out int resto)
{
    if (b == 0)
    {
        quociente = resto = 0;  // out obriga a atribuir mesmo na falha
        return false;
    }
    quociente = a / b;
    resto = a % b;
    return true;

    => string.Join(separador, Enumerable.Repeat(texto, vezes));

if (!TentarDividir(1, 0, out _, out _))

Console.WriteLine(Repetir("ha", 3, ""));
Console.WriteLine(Repetir("lá", separador: "-"));

Estoque com Dictionary

Escreva um programa que mantenha o estoque de uma livraria num Dictionary<string, int> (título → quantidade), processe uma lista de movimentações ("+Dom Casmurro:3", "-Vidas Secas:1") e recuse saídas maiores que o estoque. Mostre o estoque final em ordem alfabética.

var estoque = new Dictionary<string, int> { ["Dom Casmurro"] = 2, ["Vidas Secas"] = 1 };

{

    int qtd = int.Parse(partes[1]);
    int atual = estoque.GetValueOrDefault(titulo);  // 0 se o título não existe

    if (sinal == '-' && qtd > atual)
    {
        Console.WriteLine($"recusado: {m} (há {atual})");
        continue;
    }
    estoque[titulo] = atual + (sinal == '+' ? qtd : -qtd);
}

foreach (var (titulo, qtd) in estoque.OrderBy(p => p.Key))

Q13

Exceções próprias

Crie class EstoqueInsuficienteException : Exception com as propriedades Titulo e Disponivel. Escreva static void Vender(Dictionary<string, int> estoque, string titulo, int qtd) que a lance quando faltar estoque e ArgumentOutOfRangeException para quantidade menor que 1. Trate as duas de forma diferente e use finally para registrar o fim de cada tentativa.

var estoque = new Dictionary<string, int> { ["Dom Casmurro"] = 2 };

foreach (var (titulo, qtd) in new[] { ("Dom Casmurro", 1), ("Dom Casmurro", 5), ("Dom Casmurro", 0) })
{
    try
    {
        Vender(estoque, titulo, qtd);
        Console.WriteLine($"vendidos {qtd}; restam {estoque[titulo]}");
    }
    catch (EstoqueInsuficienteException e)
    {
        Console.WriteLine($"{e.Message} Disponível: {e.Disponivel}.");
    }
    catch (ArgumentOutOfRangeException e)
    {
        Console.WriteLine($"erro de programação: {e.ParamName} inválido");
    }
    finally
    {
        Console.WriteLine("  (tentativa registrada)");
    }
}

static void Vender(Dictionary<string, int> estoque, string titulo, int qtd)
{
    ArgumentOutOfRangeException.ThrowIfLessThan(qtd, 1);
    int disponivel = estoque.GetValueOrDefault(titulo);
    if (qtd > disponivel)
        throw new EstoqueInsuficienteException(titulo, disponivel);
    estoque[titulo] = disponivel - qtd;
}

class EstoqueInsuficienteException(string titulo, int disponivel)
    : Exception($"Estoque insuficiente de \"{titulo}\".")
{
    public string Titulo { get; } = titulo;
    public int Disponivel { get; } = disponivel;
}

Q14

Campo ou propriedade

Por que, em C#, os dados públicos de uma classe são expostos como propriedades (public decimal Preco { get; private set; }) e não como campos públicos? Cite duas vantagens concretas.

  • Validação e regras: uma propriedade pode ter lógica no set (recusar preço negativo) ou no get (calcular um valor), e essa lógica pode ser acrescentada depois, sem mudar quem usa a classe. Trocar um campo público por propriedade quebra a compatibilidade binária: quem foi compilado contra o campo precisa ser recompilado.
  • Acesso diferenciado: get público com private set (ou init) deixa todos lerem e só a própria classe alterar.

Além disso, data binding, serialização e muitos frameworks (WPF, EF Core) trabalham com propriedades, não com campos.

Q15

Herança ou interface

A livraria vende livros físicos e e-books. Quando modelar LivroFisico e Ebook herdando de uma classe Produto, e quando fazer os dois implementarem uma interface IVendavel? Por que o C# permite várias interfaces, mas uma só classe base?

Herança quando há uma relação "é um" com estado e comportamento comuns a reaproveitar: título, preço e as regras de desconto vivem em Produto. Interface quando o que se compartilha é só um contrato, entre tipos que podem não ter nada mais em comum: um IVendavel pode ser implementado por um livro, um vale-presente e uma assinatura. A herança simples evita o "problema do diamante" (duas bases com o mesmo membro, com implementações diferentes); as interfaces, que tradicionalmente não têm estado, podem ser combinadas à vontade. Desde o C# 8 elas podem ter implementações padrão, mas continuam sem campos de instância.

Q16

class, struct ou record

Para cada tipo da livraria, escolha class, struct, record ou record struct, justificando: (a) Cliente, com identidade e dados que mudam; (b) Isbn, um código de 13 dígitos; (c) ItemDoPedido (título, quantidade e preço unitário), comparado por valor; (d) Coordenada com dois double, criada aos milhões num mapa.

  • (a) **class**: dois clientes com o mesmo nome continuam pessoas diferentes (identidade), e o objeto muda ao longo do tempo.
  • (b) **readonly record struct*: é um valor pequeno e imutável, comparado pelo conteúdo, e vale a pena não alocar no *heap.
  • (c) **record** (classe): igualdade por valor, ToString legível e with para criar cópias alteradas, sem se preocupar com tamanho.
  • (d) **record struct** (ou struct): 16 bytes, criado em grande quantidade; como tipo de valor, fica dentro do array que o contém, sem uma alocação por coordenada para o coletor de lixo acompanhar.

Regra geral: struct só para tipos pequenos (até uns 16 bytes), imutáveis e com semântica de valor; o resto, class ou record.

Q17

Pattern matching

O que este método devolve para um Ebook de 30 reais, para um LivroFisico de 0,5 kg e para null? Por que a ordem dos casos importa?

static decimal Frete(Produto? p) => p switch
{
    null => throw new ArgumentNullException(nameof(p)),
    Ebook => 0m,
    LivroFisico { PesoKg: <= 1 } => 10m,
    LivroFisico l => 10m + (decimal)(l.PesoKg - 1) * 5m,
    _ => 15m,
};
  • Ebook de 30 reais: 0. O padrão de tipo Ebook casa, e o preço nem é consultado.
  • LivroFisico de 0,5 kg: 10. O padrão de propriedade { PesoKg: <= 1 } casa antes do caso geral.
  • null: lança ArgumentNullException.

A ordem importa porque o primeiro caso que casa vence: se LivroFisico l viesse antes de LivroFisico { PesoKg: <= 1 }, o segundo nunca seria alcançado, e o compilador acusaria erro por isso. O _ final cobre os outros produtos (um vale-presente, por exemplo).

Q18

Pacotes e projetos

Qual a diferença entre uma solution (.sln ou .slnx), um projeto (.csproj) e um pacote NuGet? Como a livraria seria dividida em projetos, e o que significa um <PackageReference Include="Dapper" Version="2.1.66" />?

O projeto é a unidade de compilação: gera um assembly (.dll ou executável) e declara as dependências. A solution só agrupa projetos para abri-los e compilá-los juntos. Um pacote NuGet é um assembly publicado e versionado, baixado de um repositório (nuget.org). A livraria poderia ter Livraria.Dominio (biblioteca de classes, sem dependências), Livraria.Dados (que referencia o domínio e os pacotes de banco), Livraria.Api e Livraria.Testes. O PackageReference pede o pacote Dapper na versão 2.1.66; o dotnet restore o baixa, e as dependências dele vêm junto. Fixar a versão exata dá builds reprodutíveis.

Q19

Uma classe com invariante

Escreva class Livro com Titulo (obrigatório, não vazio), Preco (não negativo, com private set) e o método AplicarDesconto(decimal percentual), que aceita de 0 a 50% e arredonda para centavos. Use ArgumentException e ArgumentOutOfRangeException. Mostre uma criação válida, um desconto e duas tentativas inválidas.

var l = new Livro("Vidas Secas", 59.90m);
l.AplicarDesconto(15);
Console.WriteLine($"{l.Titulo}: R$ {l.Preco}");

try { l.AplicarDesconto(80); }
catch (ArgumentOutOfRangeException e) { Console.WriteLine($"recusado: {e.ParamName} = {e.ActualValue}"); }

try { _ = new Livro("  ", 10m); }
catch (ArgumentException e) { Console.WriteLine($"recusado: {e.Message}"); }

class Livro
{
    public string Titulo { get; }
    public decimal Preco { get; private set; }

    public Livro(string titulo, decimal preco)
    {
        ArgumentException.ThrowIfNullOrWhiteSpace(titulo);
        ArgumentOutOfRangeException.ThrowIfNegative(preco);
        Titulo = titulo;
        Preco = preco;
    }

    public void AplicarDesconto(decimal percentual)
    {
        if (percentual is < 0 or > 50)
            throw new ArgumentOutOfRangeException(nameof(percentual), percentual, "entre 0 e 50");
        Preco = Math.Round(Preco * (1 - percentual / 100), 2, MidpointRounding.AwayFromZero);
    }
}

recusado: percentual = 80

Q24

Por que genéricos

Antes dos genéricos (C# 2), a coleção padrão era o ArrayList, que guarda object. Cite dois problemas que a List<int> resolve em relação a ele.

  • Segurança de tipo: no ArrayList cabe qualquer coisa; um string inserido por engano numa lista de números só é descoberto em execução, no cast (int)lista[i], que lança InvalidCastException. Na List<int>, é erro de compilação.
  • Desempenho: guardar um int como object exige boxing (uma alocação no heap por número) e unboxing na leitura. A List<int> guarda os int direto num array interno, sem alocação por elemento.

Ao contrário dos templates do C++, os genéricos do .NET existem em tempo de execução: o JIT gera código especializado para tipos de valor e compartilha uma única versão entre os tipos de referência.

Q25

Func, Action e Predicate

O que representam Func<int, int, int>, Action<string> e Func<Livro, bool>? Escreva uma lambda compatível com cada um.

  • Func<int, int, int>: recebe dois int e devolve um int (o último parâmetro de tipo é o retorno). Ex.: (a, b) => a + b.
  • Action<string>: recebe uma string e não devolve nada. Ex.: msg => Console.WriteLine(msg).
  • Func<Livro, bool>: um predicado sobre livros, usado no Where. Ex.: l => l.Preco < 50m. O Predicate<Livro> tem a mesma assinatura, mas é outro tipo e não converte implicitamente; por isso o LINQ usa Func.
Q26

Execução adiada

Por que este código imprime 3, e não 2? O que muda com .ToList() no fim da primeira linha?

var lista = new List<int> { 1, 2, 3, 4 };
var grandes = lista.Where(x => x > 2);
lista.Add(5);
Console.WriteLine(grandes.Count());

O Where não filtra nada na hora: devolve um objeto que descreve a consulta. Ela só executa quando alguém percorre o resultado, aqui no Count(), e nesse momento a lista já tem o 5: os maiores que 2 são 3, 4 e 5. Com .ToList() no fim da primeira linha, a consulta executa imediatamente e o resultado é materializado numa lista nova; o Add posterior não a afeta, e o programa imprime 2. A execução adiada também significa que percorrer grandes duas vezes executa o filtro duas vezes, o que importa quando a fonte é um banco de dados.

Q27

Nullable reference types

Com <Nullable>enable</Nullable>, qual a diferença entre string e string?? O que o operador ! (null-forgiving) faz, e por que usá-lo com moderação?

Com o recurso ativo, string declara que a variável nunca deve ser nula e string? que pode ser. O compilador faz uma análise de fluxo e avisa quando um string? é usado sem verificação, ou quando null é atribuído a um string. Os avisos não mudam nada em execução: os dois tipos são a mesma string. O ! diz ao compilador "confie em mim, aqui não é nulo" e silencia o aviso, sem nenhuma verificação real. Se a afirmação estiver errada, a NullReferenceException volta. Use-o só quando você sabe algo que o compilador não consegue deduzir, e prefira reescrever o código para que ele deduza.

Q34

Gerações do coletor de lixo

Explique as gerações 0, 1 e 2 do coletor de lixo do .NET e a hipótese em que elas se apoiam. O que é o LOH?

A hipótese geracional diz que a maioria dos objetos morre jovem. Objetos novos nascem na geração 0, que é pequena e coletada com frequência e rapidez. Quem sobrevive a uma coleta sobe para a geração 1 (um "amortecedor") e, sobrevivendo de novo, para a 2, coletada raramente, porque objetos antigos tendem a continuar vivos. Assim, a maioria das coletas examina só uma pequena parte do heap. O LOH (Large Object Heap) guarda objetos a partir de 85.000 bytes, como arrays grandes: eles já nascem lógicamente na geração 2 e, por padrão, não são compactados, porque mover blocos grandes é caro. Alocar e descartar muitos arrays grandes fragmenta o LOH, e é aí que entram o ArrayPool<T> e o Span<T>.

Q35

IDisposable e using

Se o .NET tem coletor de lixo, por que existe IDisposable? O que using var arquivo = File.OpenRead(...) garante, e o que é um finalizer?

O coletor cuida de memória gerenciada, e só quando quiser. Arquivos, sockets, conexões de banco e travas são recursos não gerenciados ou escassos: precisam ser liberados assim que deixam de ser usados, e não "algum dia". O IDisposable.Dispose() é a liberação explícita, e o using garante a chamada no fim do escopo, mesmo com exceção (é o RAII do C#, mas opcional). O finalizer (~Classe()) é uma rede de segurança chamada pelo coletor antes de recuperar um objeto que não foi descartado; é lento, não tem hora certa e atrasa a coleta. O padrão é: Dispose libera e chama GC.SuppressFinalize(this); o finalizer, quando existe, só cobre o esquecimento.

Q36

async não é thread

"Um método async roda em outra thread." Por que a frase está errada? O que acontece de fato num await File.ReadAllTextAsync(...) quando o arquivo ainda não foi lido?

O async não cria thread nenhuma: ele transforma o método numa máquina de estados que pode ser pausada. O método roda na thread de quem chamou até o primeiro await de uma operação que ainda não terminou. Nesse ponto, ele registra a continuação (o resto do método) e devolve uma Task incompleta para quem chamou: a thread fica livre para outras tarefas. A leitura acontece no sistema operacional, sem thread nenhuma esperando bloqueada. Quando o SO avisa que terminou, a continuação é agendada (no thread pool, num servidor; na thread da interface, num app gráfico) e o método segue de onde parou. É assim que um servidor atende milhares de requisições com poucas dezenas de threads.

Q37

Task.Run e async void

Por que Task.Run não deve envolver chamadas de E/S num servidor ASP.NET Core, e por que async void só é aceitável em handlers de evento?

O Task.Run empurra um trabalho para outra thread do thread pool. Para trabalho de CPU num app de interface, isso libera a thread da tela. Mas num servidor, onde a requisição já roda no thread pool, envolver E/S em Task.Run só troca uma thread por outra e acrescenta custo; o certo é chamar a versão assíncrona de verdade (ReadAsync, QueryAsync). Já o async void não devolve Task: quem chama não pode aguardar o fim, e uma exceção lançada dentro dele não tem para onde ir e derruba o processo. Existe porque handlers de evento precisam devolver void; em qualquer outro lugar, async Task.

Q38

lock e o que ele protege

O que lock (_trava) { ... } garante, e por que a trava deve ser um objeto privado, e não this ou um string? O que o .NET 9 trouxe para isso?

O lock garante exclusão mútua: só uma thread por vez executa os blocos protegidos pela mesma trava, e as escritas feitas dentro dele ficam visíveis para a próxima thread que entrar. Travar this ou um typeof(...) expõe a trava a qualquer código de fora, que pode travar o mesmo objeto e causar deadlocks difíceis de achar; uma string literal é compartilhada pelo processo inteiro (interning). Um campo private readonly garante que só a própria classe usa aquela trava. O .NET 9 trouxe o tipo System.Threading.Lock, feito só para isso: private readonly Lock _trava = new(); funciona com o mesmo lock e é mais eficiente que travar um object.

Q45

Fact, Theory e o padrão AAA

No xUnit, qual a diferença entre [Fact] e [Theory] com [InlineData]? O que é o padrão Arrange, Act, Assert?

O [Fact] é um teste sem parâmetros, que verifica uma afirmação sempre verdadeira. A [Theory] é um teste parametrizado: o mesmo método roda uma vez para cada [InlineData(...)], e cada execução aparece como um teste separado no relatório. É ideal para uma regra com vários casos (o frete de cada UF, os limites de um desconto). O padrão AAA organiza o corpo em três blocos: Arrange (montar os objetos e os dados), Act (executar a ação testada, de preferência numa linha só) e Assert (verificar o resultado). Um teste que tem vários "Act" geralmente são vários testes.

Q46

SQL injection

Mostre por que o código abaixo é vulnerável, o que um atacante digitaria e como o ADO.NET resolve o problema.

var cmd = conexao.CreateCommand();
cmd.CommandText = $"SELECT * FROM clientes WHERE email = '{email}'";

O valor digitado vira parte do comando SQL. Com o e-mail ' OR '1'='1, a consulta fica ... WHERE email = '' OR '1'='1', que devolve todos os clientes. Com '; DROP TABLE clientes; --, conforme o banco, o atacante executa um comando novo. A correção é o parâmetro: cmd.CommandText = "SELECT * FROM clientes WHERE email = $email"; cmd.Parameters.AddWithValue("$email", email);. O texto do comando e o valor viajam separados; o banco nunca interpreta o valor como SQL, qualquer que seja o conteúdo. A interpolação de string é o erro mais comum, justamente porque o $"..." parece inofensivo.

Q47

ADO.NET, Dapper ou EF Core

Compare ADO.NET puro, Dapper e EF Core quanto ao que você escreve, ao controle sobre o SQL e ao que cada um faz por você. Quando escolher cada um?

  • ADO.NET: você escreve o SQL e também o código de leitura linha a linha (reader.GetString(0)). Controle total e nenhuma dependência, mas muito código repetitivo.
  • Dapper: você escreve o SQL; ele mapeia parâmetros e resultados para objetos (conexao.Query<Livro>(sql, new { id })). Quase a velocidade do ADO.NET, sem a cerimônia.
  • EF Core: você escreve LINQ, e ele gera o SQL; acompanha as mudanças dos objetos (change tracking), gera migrations do esquema e cuida dos relacionamentos. Mais produtivo para CRUD, e o SQL fica menos visível.

Escolha EF Core para aplicações com muitas entidades e regras de negócio, Dapper para consultas de leitura sob medida ou de desempenho crítico, e ADO.NET quando não puder ter dependências. Elas convivem: é comum usar EF Core para escrever e Dapper para relatórios.

Q48

O problema N+1

O que é o problema N+1 no EF Core? Mostre o código que o causa e duas formas de corrigir.

Ao listar N pedidos e acessar pedido.Cliente.Nome de cada um com lazy loading, o EF executa uma consulta para os pedidos e mais uma para cada cliente: N+1 idas ao banco, cada uma com a sua latência de rede. Com 500 pedidos, 501 consultas. Correções:

  • **Include**: db.Pedidos.Include(p => p.Cliente).ToList() traz tudo num JOIN;
  • projeção: db.Pedidos.Select(p => new { p.Id, ClienteNome = p.Cliente.Nome }).ToList() traz só as colunas usadas, também numa consulta.

Para leitura sem alteração posterior, AsNoTracking() ainda evita o custo do change tracking. O ToQueryString() ou o log do EF mostram o SQL realmente gerado.

Q49

Documento ou relacional

A livraria guarda pedidos com itens. Quando modelar no MongoDB, com os itens embutidos no documento do pedido, é melhor que no PostgreSQL, com tabelas pedidos e itens? E quando é pior?

Melhor quando os dados são lidos e gravados juntos: o pedido é sempre exibido com os itens, e os itens não existem fora dele. Um documento traz tudo numa leitura só, sem join, e a estrutura pode variar entre pedidos (um item com dedicatória, outro com embrulho). Pior quando há relações entre entidades independentes e consultas transversais: "quantos exemplares de Vidas Secas vendemos este mês, por região?" exige agregações sobre todos os documentos, e o título de um livro repetido em milhares de pedidos precisa ser atualizado em todos. O relacional garante integridade (chaves estrangeiras, transações entre tabelas) e consultas ad hoc; o documento ganha em leitura do agregado e em flexibilidade de esquema.

Q54

A ordem dos middlewares

O pipeline do ASP.NET Core é uma sequência de middlewares. Por que app.UseAuthentication() precisa vir antes de app.UseAuthorization(), e o que acontece se um middleware não chamar next()?

Cada middleware recebe a requisição, pode fazer algo antes, chama o próximo (await next(context)) e pode fazer algo depois, na volta: o pipeline é uma pilha de chamadas aninhadas. A autenticação descobre quem é o usuário (lê o cookie ou o token e preenche HttpContext.User); a autorização decide se ele pode acessar o endpoint. Com a ordem invertida, a autorização olharia para um usuário ainda anônimo e recusaria tudo. Um middleware que não chama next() encerra o pipeline (short-circuit): é o que fazem os arquivos estáticos ao achar o arquivo, o rate limiter ao devolver 429 e a autorização ao devolver 401 ou 403.

Q55

Entidade ou DTO

Por que a API da livraria não deve receber nem devolver diretamente a entidade Livro do EF Core? O que é um DTO, e que ataque o overposting permite?

A entidade é o modelo interno: tem chaves estrangeiras, propriedades de navegação, campos de auditoria e regras que mudam com o banco. Expô-la acopla o contrato público ao esquema (mudar uma coluna quebra os clientes) e pode vazar dados (o custo de aquisição, por exemplo). Um DTO (Data Transfer Object) é um tipo feito só para o contrato: CriarLivroRequest(string Titulo, decimal Preco) na entrada e LivroResponse(...) na saída. O overposting acontece quando a API faz binding da entidade inteira: o cliente envia um campo que não deveria poder definir, como "Destaque": true ou "Preco": 0, e ele é gravado. Com um DTO de entrada, só os campos previstos existem.

Q56

Concorrência otimista com ETag

Dois atendentes abrem o mesmo livro, e cada um altera o preço e salva. Como ETag e If-Match evitam que a segunda gravação apague a primeira sem ninguém perceber? Que código HTTP a API devolve?

No GET, a API devolve o recurso com um ETag, uma versão (um contador ou um hash do conteúdo, como o RowVersion do EF). No PUT, o cliente envia If-Match: <etag que ele leu>. A API só grava se a versão atual ainda for aquela; senão, devolve 412 Precondition Failed. O primeiro atendente grava e muda a versão; o segundo recebe 412, recarrega e decide. É concorrência otimista: nada é travado durante a edição, e o conflito é detectado na gravação. Sem isso, vale a "última gravação", que perde dados em silêncio.

Q57

O que um JWT protege

Um JWT tem três partes separadas por ponto. O que cada uma contém, e por que é um erro guardar a senha ou o CPF do usuário dentro dele?

O cabeçalho (algoritmo), o payload (as claims: sub, role, exp...) e a assinatura. As duas primeiras são só JSON em Base64Url: qualquer um que tenha o token consegue lê-las, sem chave nenhuma. A assinatura garante a integridade (ninguém altera o payload sem invalidá-la), não o sigilo. Por isso dado sensível nunca vai no JWT. A API valida assinatura, emissor, audiência e validade (exp) a cada requisição; como o token não pode ser revogado antes de expirar sem um controle extra, o token de acesso deve durar pouco (minutos) e ser renovado com um refresh token.

Q58

De onde vem a configuração

No ASP.NET Core, a mesma chave pode vir do appsettings.json, do appsettings.Production.json, de variáveis de ambiente e da linha de comando. Qual vence, e onde deve ficar a connection string de produção?

As fontes são lidas em ordem, e a última vence: appsettings.json, depois appsettings.{Ambiente}.json, depois user secrets (só em desenvolvimento), variáveis de ambiente e, por fim, argumentos de linha de comando. A chave aninhada ConnectionStrings:Livraria vira a variável de ambiente ConnectionStrings__Livraria (dois sublinhados). A connection string de produção, com senha, não vai para nenhum arquivo versionado: vem de variável de ambiente, de um cofre de segredos (Azure Key Vault, AWS Secrets Manager) ou do orquestrador. O appsettings.json do repositório guarda só valores de desenvolvimento e padrões sem segredo.

Q59

Cache: o problema difícil

"Há duas coisas difíceis em computação: invalidar cache e dar nomes às coisas." Ao guardar o catálogo da livraria no Redis, que estratégias existem para que um preço alterado não continue aparecendo velho, e o que é uma cache stampede?

  • Expiração (TTL): o item some depois de N minutos. Simples, mas aceita um atraso de até N minutos.
  • Invalidação explícita: quem altera o preço apaga (ou atualiza) a chave do livro. Exige que todo caminho de escrita lembre de invalidar.
  • Etiquetas: o HybridCache (.NET 9) permite invalidar todas as entradas de uma etiqueta ("catalogo") de uma vez.

A cache stampede acontece quando uma chave muito usada expira e centenas de requisições simultâneas encontram o cache vazio e vão todas ao banco ao mesmo tempo. O HybridCache evita isso: só uma requisição calcula o valor, e as outras aguardam o resultado dela.

Q60

Entrega pelo menos uma vez

O RabbitMQ garante entrega "pelo menos uma vez" quando o consumidor só confirma (ack) depois de processar. Por que isso obriga o consumidor que envia o e-mail de confirmação de pedido a ser idempotente, e como fazê-lo?

Se o consumidor processa a mensagem e cai antes de enviar o ack, o RabbitMQ entrega a mesma mensagem de novo, para ele ou para outro consumidor: o cliente receberia dois e-mails. Não há como garantir "exatamente uma vez" só com a fila. Ser idempotente significa que processar a mesma mensagem duas vezes tem o mesmo efeito que uma: cada mensagem carrega um identificador único (o id do pedido mais o tipo do evento), e o consumidor registra os ids já processados, de preferência na mesma transação do efeito, e ignora repetidos.

Q61

gRPC ou REST

Para a comunicação entre o serviço de pedidos e o de estoque, por que gRPC pode ser melhor que uma API REST com JSON? Por que ele não costuma ser usado diretamente pelo navegador?

O gRPC usa Protocol Buffers, um formato binário compacto e rápido de serializar, sobre HTTP/2, com várias chamadas multiplexadas numa conexão e streaming nos dois sentidos. O contrato (.proto) é a fonte da verdade: cliente e servidor são gerados a partir dele, com tipos verificados na compilação. Entre serviços internos, isso significa menos banda, menos CPU e menos erros de integração. O navegador não dá ao JavaScript o controle sobre os quadros HTTP/2 de que o gRPC precisa; é preciso o gRPC-Web, com um proxy ou suporte no servidor. Para APIs públicas, REST com JSON continua mais simples de consumir e depurar.

Q66

Post, Redirect, Get

Depois de processar o formulário de "finalizar pedido", por que a página deve responder com um redirecionamento (303 ou 302) para uma página de confirmação, e não renderizar a confirmação direto?

Se a resposta ao POST for a própria página, o navegador guarda o POST como última ação: um F5 (ou o botão voltar e avançar) reenvia o formulário, e o cliente pode criar o pedido duas vezes (o navegador até avisa "deseja reenviar os dados?"). Com o padrão PRG, o POST processa e responde 303 See Other com Location: /pedidos/123/confirmacao; o navegador faz um GET nessa URL, e recarregar a página só repete o GET, que é inofensivo. Nas Razor Pages, isso é return RedirectToPage("Confirmacao", new { id }). O PRG não substitui a idempotência no servidor: um duplo clique rápido ainda pode enviar dois POST.

Q67

O token antiforgery

O que o token antiforgery das Razor Pages protege, e por que ele não é necessário numa API que só aceita Authorization: Bearer?

Ele protege contra CSRF: um site malicioso faz o navegador da vítima enviar um formulário para a livraria, e o navegador anexa sozinho o cookie de sessão. O token é um valor secreto embutido no formulário (um campo oculto) e conferido no servidor; o site atacante não consegue lê-lo, então não consegue forjar uma requisição válida. As Razor Pages o incluem e validam automaticamente nos formulários. Uma API autenticada por Bearer não sofre CSRF porque o navegador não anexa esse cabeçalho sozinho: o JavaScript da própria aplicação precisa colocá-lo. O risco volta se a API também aceitar cookies.

Q68

Modos de renderização do Blazor

Compare os modos Static SSR, Interactive Server e Interactive WebAssembly do Blazor quanto a onde o código roda, latência das interações e custo para o servidor. Qual usar na página de um livro, no carrinho e no painel administrativo?

  • Static SSR: o componente é renderizado em HTML no servidor, sem interatividade (como Razor Pages). Rápido e barato. Bom para a página do livro, que precisa ser indexada e carregar rápido.
  • Interactive Server: o componente roda no servidor e mantém uma conexão SignalR (um circuito) com o navegador; cada clique viaja até o servidor e volta. Sem download inicial, mas cada usuário conectado consome memória no servidor, e a latência de rede aparece em cada interação. Bom para o painel administrativo: poucos usuários, acesso direto a dados e regras no servidor.
  • Interactive WebAssembly: o .NET roda no navegador. As interações são locais, sem custo de servidor, mas há um download inicial grande, e o código fica exposto ao usuário. Bom para o carrinho, se ele precisar ser muito responsivo (e o modo Auto começa no servidor e passa para WebAssembly depois do download).
Q69

Cache condicional

O site consulta GET /livros/1 na API a cada visita. Como ETag e If-None-Match economizam banda, e que código a API devolve quando nada mudou?

Na primeira resposta, a API envia o ETag. O site (ou o HttpClient com um cache próprio) guarda o corpo e o ETag; na próxima vez, envia If-None-Match: "<etag>". Se a versão não mudou, a API responde 304 Not Modified sem corpo, e o site reaproveita o que tinha. Ainda há uma ida à rede, mas sem transferir o conteúdo, e a API pode responder sem montar o JSON. É o mesmo ETag da concorrência otimista, usado para outro fim: no If-Match, ele protege a escrita; no If-None-Match, economiza na leitura.

Q74

A regra da thread de interface

Por que um clique que faz var dados = http.GetStringAsync(url).Result; congela a janela, e por que alterar um controle a partir de uma thread de segundo plano lança exceção?

Os frameworks de interface têm uma única thread de interface, que processa os eventos (cliques, redesenho) num laço. O .Result bloqueia essa thread até a resposta chegar: nesse intervalo nenhum evento é processado, e a janela "não responde". Pior, se a continuação precisar voltar para a mesma thread, o resultado é um deadlock. O certo é var dados = await http.GetStringAsync(url);: a thread fica livre durante a espera, e o código depois do await volta a rodar nela. Os controles não são seguros para acesso concorrente; por isso só a thread de interface pode alterá-los, e quem está em outra thread precisa despachar a alteração (Dispatcher.UIThread.Post no Avalonia, MainThread.BeginInvokeOnMainThread no MAUI).

Q75

Por que MVVM

O que o padrão MVVM separa, e qual a vantagem concreta de ter a lógica do caixa num ViewModel em vez de nos eventos de clique da janela?

O MVVM separa a View (o XAML, só aparência), o ViewModel (o estado da tela e os comandos, em C# puro, sem referência a controles) e o Model (domínio e dados). A View se liga ao ViewModel por data binding: quando uma propriedade muda e o ViewModel avisa por INotifyPropertyChanged, a tela se atualiza sozinha; quando o usuário aciona um botão, um ICommand do ViewModel é executado. A vantagem concreta é que o ViewModel pode ser testado sem abrir janela nenhuma: "adicionar um item soma o total", "o botão Finalizar fica desabilitado com o carrinho vazio". Com a lógica nos eventos de clique, o teste exigiria automatizar a interface, e a mesma lógica não poderia ser reaproveitada na versão MAUI.

Q79

Por que não alocar no loop

Um jogo roda a 60 quadros por segundo e cria, a cada quadro, uma List<Inimigo> temporária e algumas strings para o placar. Por que isso causa "engasgos" periódicos, e que técnicas evitam o problema?

Cada alocação vai para a geração 0 do heap. Alocando a cada quadro, a geração 0 enche a cada poucos segundos e o coletor de lixo roda; uma coleta, mesmo curta, pode levar alguns milissegundos, e um quadro a 60 FPS tem só 16,7 ms. O resultado é um engasgo perceptível em intervalos regulares. Técnicas:

  • reaproveitar coleções: uma List como campo, com Clear() a cada quadro, em vez de new (a capacidade interna é mantida);

Q84

Ferramentas para um modelo de IA

Num assistente da livraria feito com Microsoft.Extensions.AI, o modelo pode chamar a função BuscarLivros(string termo). Quem executa a função de fato, e que cuidados de segurança isso exige?

Q85

Medir antes de otimizar

Por que um laço com Stopwatch em volta de uma chamada é uma forma pouco confiável de comparar duas implementações, e o que o BenchmarkDotNet faz de diferente?

Uma medição ingênua mistura o tempo do JIT (a primeira chamada compila o método), sofre com o compilador eliminando código cujo resultado não é usado, mede o ruído do sistema (outros processos, frequência variável da CPU, coletas de lixo) e costuma ser feita em modo Debug. O BenchmarkDotNet roda cada caso num processo separado, em Release, faz o aquecimento, repete até a medida estabilizar, consome os resultados para que não sejam eliminados e relata média, desvio e, com [MemoryDiagnoser], os bytes alocados por operação. É a diferença entre uma impressão e uma medida.

Q86

Native AOT: o que se ganha e o que se perde

O que muda ao publicar uma ferramenta de linha de comando com PublishAot=true? Cite dois ganhos e duas restrições.

O código é compilado para código de máquina antes da execução, num executável único, sem JIT e sem precisar do runtime instalado. Ganhos: partida quase instantânea (milissegundos, contra dezenas ou centenas com JIT), ótima para ferramentas de terminal e funções serverless; e menor uso de memória, com um executável que não exige o .NET instalado. Restrições: reflexão dinâmica e geração de código em execução ficam limitadas (é por isso que os programas de arquivo único deste caderno precisaram de PublishAot=false para JSON por reflexão e EF Core); e o executável é específico de uma plataforma (um build para Linux x64, outro para Windows ARM64). Bibliotecas que dependem de reflexão precisam de alternativas com source generators.

record Resultado(decimal Valor, string? Erro)
{
    public static Resultado Ok(decimal v) => new(v, null);
    public static Resultado Falha(string e) => new(0, e);
}

class Calculadora
{
    public decimal Ans { get; private set; }

    public Resultado Avaliar(string linha)
    {
        var p = linha.Split(' ', StringSplitOptions.RemoveEmptyEntries);
        Resultado r = p switch
        {
            ["raiz", var x] => Numero(x) is { } v ? Raiz(v) : Resultado.Falha("operando não é um número"),
            [var a, var op, var b] => Numero(a) is { } va && Numero(b) is { } vb ? Operar(op, va, vb)
                                                                              : Resultado.Falha("operando não é um número"),
            _ => Resultado.Falha("use \"a op b\" ou \"raiz a\""),
        };
        if (r.Erro is null)
            Ans = r.Valor;  // só um resultado válido substitui o ans
        return r;
    }

    private decimal? Numero(string texto) =>
        texto == "ans" ? Ans
        : decimal.TryParse(texto.Replace(',', '.'), NumberStyles.Number, CultureInfo.InvariantCulture, out var v) ? v
        : null;

    private static Resultado Raiz(decimal x) =>
        x < 0 ? Resultado.Falha("raiz de número negativo") : Resultado.Ok((decimal)Math.Sqrt((double)x));

    private static Resultado Operar(string op, decimal a, decimal b)
    {
        try
        {
            return op switch
            {
                "+" => Resultado.Ok(a + b),
                "-" => Resultado.Ok(a - b),
                "*" => Resultado.Ok(a * b),
                "/" => b == 0 ? Resultado.Falha("divisão por zero") : Resultado.Ok(a / b),
                "%" => Resultado.Ok(a * b / 100),
                "^" => b != decimal.Truncate(b) ? Resultado.Falha("o expoente precisa ser inteiro") : Resultado.Ok(Potencia(a, (int)b)),
                _ => Resultado.Falha("operação desconhecida (use + - * / ^ % ou raiz)"),
            };
        }
        catch (OverflowException)
        {
            return Resultado.Falha("resultado grande demais");
        }
    }

    private static decimal Potencia(decimal a, int n)
    {
        if (n < 0)
            return 1 / Potencia(a, -n);
        decimal r = 1;
        checked
        {
            for (int i = 0; i < n; i++)
                r *= a;  // decimal estoura com OverflowException
        }
        return r;
    }
}

A livraria de ponta a ponta

Caminho da solução

  • Projetos: Livraria.Dominio (entidades e regras, sem dependências), Livraria.Api (endpoints, EF Core, o worker), Livraria.Cliente (terminal com HttpClient) e Livraria.Testes. Use DTOs nos endpoints, nunca as entidades (módulo 6).

  • Worker: um BackgroundService lê o canal com ReadAllAsync(stoppingToken) e registra o envio em log. Se o processo cair entre gravar o pedido e publicar o evento, o e-mail se perde: a correção profissional é o padrão outbox (gravar o evento numa tabela na mesma transação e publicá-lo depois).
  • Cliente: HttpClient com AddStandardResilienceHandler (repetição e timeout), GetFromJsonAsync<List<LivroResponse>> e tratamento do ProblemDetails nos erros 400 e 409.
  • Testes: WebApplicationFactory<Program> sobe a API em memória; troque a conexão do EF por um SQLite em memória por teste (ConfigureServices no WithWebHostBuilder). Teste o caminho feliz do pedido, o 400 de quantidade inválida, o 404 de livro inexistente e o conflito de estoque com dois pedidos concorrentes do último exemplar.
  • Execução: o .NET Aspire (módulo 7) sobe a API, o worker e um PostgreSQL com um só dotnet run do projeto AppHost, com o painel de logs e traces do OpenTelemetry. Sem Aspire e sem Docker, rode a API com dotnet run --project Livraria.Api e o cliente com dotnet run --project Livraria.Cliente em dois terminais, com o SQLite em arquivo.
